# c1 Aiterm公開面へのPeertable実席接続

実施日: 2026-08-12

## 実測

- Aiterm MCP diagnostics は `version: 0.24.0`、`overall: ready`、MCP tool call は `ready` を返した。
- 破棄可能な Aiterm-managed Codex session `c1-agent-configure-fixture` を
  `gpt-5.6-luna / medium` で起動した。
- 公開 `agent_configure` は、いずれも同じ `session_id` と
  `aiterm.agent-configure-result.v1` receipt を返した。
  - model-only: `model: gpt-5.6-terra`
  - effort-only: `reasoning_effort: high`
  - 同時変更: `model: gpt-5.6-luna`, `reasoning_effort: low`
- 同sessionの画面には順に `Model changed to gpt-5.6-terra medium`、
  `Model changed to gpt-5.6-terra high`、`Model changed to gpt-5.6-luna low` が残り、
  最終入力欄も同じ session のまま表示された。session 再作成は観測していない。

## 正規launchとの相関

`mcp__aiterm__pty_list` では現行Peertable席 `peertable-c1` は通常PTY（`zsh`）として列挙された。
現行 `skill/scripts/launch-seat.sh` は `peer-$name` tmux sessionを作り、Claude／Codex CLIを
そのpaneへ直接送る。room member metadataは `observe.tmux_socket` と `observe.tmux_target` だけで、
`session_id`、`agent_session`、`vendor_session` を保存しない。

`node experiments/live-seat-config-c1-repro.mjs` はこの境界を4/4で確認した。

## 結論

Aiterm公開 `agent_configure` の model-only／effort-only／同時変更は managed agent session に対して成立する。
しかし現行Peertable正規launchはその managed `session_id` を保持・公開していないため、同入口を現行席へ
渡す正確な相関は未成立である。c2はPLAN 2.1のとおり、Aiterm公開launcherで managed席を作るための
最小adapterだけを検討対象とする。製品コード、旧t4、既存run、既存差分は変更していない。
