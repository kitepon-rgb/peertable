# r4 — Codex room MCPへseat固有環境を明示

実施日: 2026-08-12

## 原因と修正

- r3後の親live再着席で、Codexはprojectの`room` MCPを認識したがinitialize前にclientが終了し、
  member登録は起きなかった。
- 破棄可能なAiterm診断席の実起動コマンドと画面から、Aitermの新tmuxへ`AITERM_*`は渡る一方、
  launcher呼出しprocessの`PEERTABLE_*`はCodex子へ継承されず、room clientの必須環境が欠けると確定した。
- 正規launchはcredential fileを準備した後、Aiterm起動と同じseat環境をCodex project room MCPの明示env tableへ
  固定する。token値は書かず0600 credential fileのpathだけを渡す。`TMUX`／`TMUX_PANE`はCodex席の実環境から
  継承する。
- project設定は席の起動直前にだけ作り、次席のlaunchで更新する。起動済みMCPは自分の環境を保持する。
  teardownはr3で導入したPeertable所有markerによりblockとgit excludeだけを撤去する。

更新したharnessは、明示env tableにmemberとcredential file pathが入り、`TMUX_PANE`だけが継承指定に残ること、
既存configのbyte復元、対象repoのgit exclude所有、実Codex CLIによるroom認識を確認した。

## 親live診断席

- Aiterm管理`peer-r4-probe`をTerra/highで起動した。
- Codex画面のMCP startup失敗一覧から`room`が消え、実roomへ`probe-r4`がvendor/model/effort/roleと
  正しいtmux観測付きで登録された。
- 診断後にAiterm session、room member、credential file、project configを撤去し、残存なしを確認した。

- Aiterm本体、実円卓席、`change-seat.sh`、旧t4所有物には書込みをしていない。
- 対象差分の`git diff --check`は成功した。正式な全席再着席とmodel／effort変更はi1で親が行う。
