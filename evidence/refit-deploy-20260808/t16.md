# t16 証跡 — peertable の deploy を image-pull 型へ移行

担当: mio / plan: refit-deploy-20260808 / 2026-08-09
commit `e6a6022`（`deploy/compose.yaml` +`deploy/README.md`）／本番 image `peertable-room:20260809-7a601a1`

**本番ホストでの build をやめた。** image は開発機で焼き、`docker save | ssh docker load` で運び、MS-A2 では `compose up` だけを叩く形へ移した。2026-08-08 の ext4 障害で build 同居のコストが顕在化したことへの構造対処（因果は未確定だが、build と本番常駐を同じホストに置く理由が元から無い）。

## 何を変えたか

**`deploy/compose.yaml`**: `build: ../room` を**キーごと削除**し、`image: peertable-room:<日付-短sha>` へ。**`build:` を残さないのが要点**——残すと本番で `compose up` した時に焼き始めるので、t16 の目的そのものが崩れる。理由をコメントで書いた。

**`deploy/README.md`（新規）**: build → save|load → `compose up` の3手順と rollback。前 campaign の t7 で実測した前提を明記した——`~/peertable/` は **git 管理外**（`deploy/` と `room/` がファイルとして置かれているだけで **`git pull` は使えない**）、会話ログは named volume で image 入替では消えない、Mac は Apple Silicon で MS-A2 は amd64。

**タグは `日付-短sha`。`latest` は使わない**——どの commit が本番に居るか分からなくなるので。

## 罠を3件、手順書へ焼き込んだ

1. **`docker build` で代用しない・`docker-buildx` を直接叩く。** Apple Silicon + Colima では legacy builder の `--platform linux/amd64` が信頼できない（罠DB `docker-legacy-builder-on-apple-silicon-…`）。加えて**この開発機では `docker buildx` が `unknown command`** で、実在するのは standalone の `/opt/homebrew/bin/docker-buildx`（v0.36.0）だけ（rin の実測）。**プラグイン配置を前提にすると新しい環境変更が要るので、現ホストの正規入口をそのまま書いた**
2. **`--load` を明示する。** 直後に `docker save` するので、driver 差に依存せずローカルの image store へ載せる必要がある（`--load` = `--output=type=docker`）。付けないと build は成功しても `docker save` で image が見つからない
3. **検証用 room サーバーの罠2つ**——`PEERTABLE_POST_TOKEN` は**空文字と未設定が別物**（空文字を渡すと「空文字のトークンを要求する」状態になり全書込が 403）／落ちた検証 server がポートを掴んだまま残ると、`stdio` を捨てている限り `EADDRINUSE` が見えず **curl が前の壊れた server に当たる**（卓で計3回踏まれている）

## ロールバック

**旧 image `peertable-room:local`（232MB）が MS-A2 に残っている。** `image:` を戻して `up -d` すれば戻る。**入替前に `docker images` で戻り先の実在を確認してから叩いた**——README にも「戻り先が無い状態で切り替えない」と書いた。

## 事故を1件起こした（隠さず書く）

**「今から落とす」を宣言した直後の1回目、`rsync` が失敗していて入替が起きていなかった。**

```
rsync … warning: child exited with status 23 ／ total size is 0
docker compose up -d room → Container peertable-room **Running**（＝何もしていない）
docker ps → Up 2 hours ／ image: peertable-room:local
```

**原因は cwd。** 直前の確認で `cd deploy` を叩いていて、その cwd が残ったまま `rsync deploy/compose.yaml` を実行した——`deploy/deploy/compose.yaml` を探して見つからず終わった。

**この事故が今日の型そのものである理由**:
- **`up -d` は成功を返した**（`Running`・rc=0）——**「変更が無いので何もしなかった」を、成功と区別できない形**で
- 気づけたのは **`docker ps` で image タグを見ていたから**。見ていなければ「入れ替わった」と報告していた
- **`rsync` の warning は stderr に出ていた**のに、**`tail -2` で切り落として `total size is 0` しか読んでいなかった**

room [541] で即座に訂正し、cwd を直して2回目で入れ替えた（`Recreate → Started`）。**1回目で room は一度も落ちていない**ので、卓が取った before の基準値はそのまま有効だった。

## 必要条件の書き漏らし（もう1件）

blocked にした時、工程 note へ必要条件を2つ書いた（colima 起動の裁定・`docker-buildx` の入口）。**3つ目（VM のディスクに空きがあること）が抜けていた。**

**MS-A2 側の戻り先は `docker images` で確認したのに、手元の VM の空きは見ていない**——同じ確認を片側でしかやっていなかった。build を叩いて `no space left on device` で初めて分かった。

**そして「読める数字」と「実際に空く量」も別だった**: `docker system df` の `RECLAIMABLE`（Images 1.617GB / Build Cache 67.3MB）だけを見ていたら「1.6GB 空くかも」と読んで image を消しに行っていた。**実際に prune を叩いて初めて、cache 側では届かないと分かった。**
