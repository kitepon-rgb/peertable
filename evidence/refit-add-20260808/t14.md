# t14 メンバーリストのモデル・エフォート表示 — haruka

## 何を作ったか

### script 側（先行 commit `80ec984`）

- **`launch-seat.sh`**: 着席後に `vendor` / `model` / `effort` を `POST /api/<room>/members` へ送る。
  加えて **`PEERTABLE_VENDOR` / `PEERTABLE_MODEL` / `PEERTABLE_EFFORT` を席の env へ export**（後述の理由で追加）
- **`parent-join.sh`**: `model` / `effort` を任意の第4・第5引数で受ける。**渡された時だけ**載せる
  （親はオーナーの対話セッションなので、script が起動時の値を知らない）

### server 側

- **`POST /api/<room>/members` を upsert にした**。`{name, ...meta}` を受け、**渡された欄だけ更新／
  渡されなかった欄は既存を保つ／`joined_at` は最初の登録を保つ**
- **`system` の「◯◯ が参加した」は本当に新規の時だけ**に変えた（kotoha [285] の要求）。
  既存メンバーへの再 POST で発言が流れると、状態を数秒ごとに送る消費者が**卓の全席を起こし続ける**
- **`GET /members` は任意欄をそのまま返す**（`{name, joined_at, ...meta}`）。既存形へ欄が増えるだけなので、
  Lattice 側の probe 判定（200＋非空の一覧）も wakeup-bridge も壊れない
- **`members.json` の旧形式（値が ISO 文字列）をそのまま読む**。読み込み時に `{joined_at}` へ正規化する

### UI

- 参加者チップの `title` に素性を足す（ホバー）。**素性を名乗っていない席は行ごと出さない**
  （空欄を「不明」として見せない）
- **タップ環境用の popover**（hover が無い端末向け）。`el()` / `textContent` 様式のままで `innerHTML` は使わない
  （kotoha が t3 で落とした道具を戻さない）。CSS は既存トークン（`--surface` / `--line` / `--dim`）だけ

### client 側

- **`room/client.mjs` が登録のたびに素性を載せる**（env から）。**これが本体の設計変更**——理由は下記。

## なぜ client にも載せたか（設計を途中で変えた）

当初は「`launch-seat.sh` が着席時に1回 POST する」だけだった。room [274]-[279] で**6席全員の
「参加した」が一斉に出る**のを観測し、member の登録が**繰り返し起きる**ことに気づいた。

- 席の client は**起動のたびに `{name}` で登録する**。素性を1回きりの経路に置くと、
  **member の状態が失われた時に二度と戻らない**
- **`launch-seat.sh` を通さずに `claude` を叩き直した席**は素性を名乗らない

**繰り返し起きる側に載せる**のが正しい形なので、`launch-seat.sh` が env へ入れ、client が登録のたびに送る。
`launch-seat.sh` の1回 POST も残した（親経路と、client が古い版の場合の保険）。

## どう確認したか（すべて実プロセス・使い捨て server と temp project）

**upsert の4条件**（`POST` → `GET` で読み返す）

| 条件 | 結果 |
| --- | --- |
| ① 新規（素性つき） | `vendor/model/effort` が入る |
| ② client 相当の `{name}` だけで再 POST | **素性が消えない** |
| ③ `status` だけ足す（kotoha の t15 相当） | **`model` が消えない**・`status` が増える |
| ④ system 発言の数 | **`◯◯ が参加した` 1件だけ**（②③では出ない） |

**旧形式の互換**: 値が ISO 文字列の `members.json` を置いて起動 → `joined_at` として読める →
**素性を後付けできる**・**system 発言は出ない**（新規扱いにならない）

**client の登録経路**（実プロセスを起動して確認）: 素性 env つきで起動 → 一覧に素性が載る →
**素性 env 無しで再起動 → 既存の素性が消えない** → system 発言は1件のまま

**launch-seat.sh の読み返し（正負両方）**
- 新 server → `metadata: claude / sonnet / high`
- **旧 server（`HEAD` の版・素性欄なし）→ `metadata は保存されなかった`**＝**欠陥を実際に検出する**

## 途中で自分が作った欠陥2件（どちらも自分で潰した）

1. **`curl … | python3 - <<'PY'` は必ず失敗する。** パイプ（データ）と heredoc（プログラム）が
   同じ stdin を奪い合う。しかも私は**その失敗を try/except で包んでいた**ので、
   **「保存されなかった」というもっともらしい答えに化けていた**——新 server でも旧 server でも
   常に同じ結論を返す、**何も検出しない検査**になっていた。データを argv で渡す形に直した。
   **ガードが失敗を隠した**形で、今日の卓が繰り返し言ってきた型そのもの
2. **存在しない CSS トークンを書いた**（`--card` / `--muted`）。この面が実際に持っているのは
   `--surface` / `--dim`。**背景が透ける popover** になるところだった。`grep` で実在を確かめて直した

**測定器の側でも1回踏んだ**: 検証に `timeout` を使ったら macOS に無く（`command not found`）、
**client が起動していないのに「登録されない」と読んだ**。バックグラウンド起動＋`kill` へ変えて測り直した。

## 監査してほしい観点（決定60 を自分に適用する）

- **任意欄を whitelist していない**（`name` 以外を全部そのまま持つ）。kotoha の `status` が
  無改修で乗るようにした判断だが、**書込はトークンで守られている**とはいえ、欄が無制限に増える。
  決定36（過剰設計禁止）と、**将来 `GET /members` が肥大する**リスクのどちらを取るかを見てほしい
- **UI の popover は実ブラウザで見ていない**。`node --check` と CSS トークンの実在確認までで、
  **描画は確認していない**——ホバー（`title`）は既存機構なので確度が高いが、popover の位置計算
  （`getBoundingClientRect` と `offsetWidth`）は**実物で見るべき**。ブラウザを起こす席が居たら
  ついでに見てほしい。私は「見ていない」と書く方を選んだ
- **`joined_at` を保つ実装が `{ joined_at: known?.joined_at ?? …, ...known, ...meta }` の順序に
  依存している**。`known` を後ろに置いたので既存値が勝つ形だが、**読みにくい**かもしれない
