# p7 親の起床注入 — 実装・受入証跡

## 結論

親セッション内のpersistent Monitorをbell宛DM番犬として運用し、親が別の編集ターンで作業中でも
bell宛DMが数秒以内に届いて返信できることを実測した。all宛は番犬へ通さず、親のコスト保護も維持した。

Desktop親へroom MCPを接続するだけではchannel pushが発火しなかったため、オーナー裁定で実装形を
親側番犬へ差し替えた。room server/clientの変更や非公式なDesktop内部APIへの依存はない。

## 実施

- 正典commit: `8934e74`（`skill/SKILL.md`、`origin/main`へpush済み）
- 着卓手順7、再着卓手順4、親のoperating notesへ次を固定した。
  - 単独bell宛と`to_names`にbellを含む複数宛だけを通す。
  - all宛、ping、親自身の発言は通さない。
  - SSE切断はeventとして親を起こし、3秒後に再接続する。
  - 番犬は常に1世代だけとし、張替え時は旧世代を先に止める。

## 受入実測

- 旧経路の陰性: room MCPを載せたDesktop親では、bell宛probe `[1476]` もall宛probe `[1477]` も
  作業中注入されなかった。親の観測結果 `[1483]` により「MCP接続だけではpushされない」を確定した。
- 陽性: 番犬設置後のbell宛DM `[1507]` は、親が`SKILL.md`を編集しているターンの最中に
  task notificationとして到着した。親は送信元koharu、宛先bell、seq、本文を識別し、数秒以内に
  `[1509]` で返信した。
- 負側: all宛 `[1477]` は親へ注入されず、親の観測 `[1483]` でも陰性だった。番犬仕様もall宛を
  filterするため、この負例をそのまま受入証拠とした。

以上により、固定した受入条件「親が作業中でもbell宛roomメッセージがそのターンに届く」と
「all宛が注入されない」を正負両方で満たした。
