# f3 launch-seat.sh が live で使えない model の席を seated 成功扱いする

担当: suzune（claude / opus / high）。

## 1. 欠陥（一次情報）

2026-08-11、fable-5 を指定した席は Claude の channels バナーが出たため `launch-seat.sh` の着席判定
（`case "$screen" in *"Channels (experimental)"*"server:room"*`）を通り、`seated:` を出して rc=0 で
成功終了した。しかしその席は**以後の全入力が model unavailable で 0 秒失敗**し、一度も仕事をしなかった
（bell, room [11]。当該席が私自身であり、opus/high で再着席した）。

バナーは **CLI プロセスが起動したこと**しか意味しない。model が live で応答するかは別の事実で、
起動シーケンスはそれを一度も確かめていなかった。

tsubaki の独立再現（room [25]）: バナーだけ出して即 exit する fake `claude` を PATH へ置くと、
`launch-seat.sh` は exit_code=0・`seated: peer-fake（claude / fable-5 / high ...）` を出す。

## 2. 直したもの

`skill/scripts/launch-seat.sh` に **model preflight** を入れた。位置は引数検証の直後、
`tmux kill-session`（旧席の回収）より**前**である。

- claude: `claude --model <model> -p "ping"`
- codex: `codex exec --model <model> --skip-git-repo-check "ping"`
- 一時ディレクトリで実行し（workspace trust ダイアログを避ける）、外部 CLI が固まった時のために
  120 秒の締切を置く。締切超過も失敗として落とす。
- 失敗したら `model が live で使えない: <vendor> / <model>（preflight rc=…・席は立てない）` と
  CLI の出力末尾を stderr へ出して rc=1 で終わる。

**畳む前に測るのが要点である。** 旧実装の順序（先に `tmux kill-session` → 起動 → 画面判定）だと、
使えない model を指定した時点で動いていた席が失われる。preflight を前へ置いたので、
`change-seat.sh` の「起動失敗 → 旧設定へ rollback」も、そもそも席を殺さずに済む。

実 CLI での境界（2026-08-11 実測）:

```
$ claude --model fable-5 -p "ping"   → rc=1（5秒）
$ claude --model opus -p "say ok"    → rc=0（8秒）"ok"
$ codex exec --model gpt-9-nonexistent --skip-git-repo-check "say ok"
    → rc=1（7秒）"The 'gpt-9-nonexistent' model is not supported when using Codex with a ChatGPT account."
```

代償: 席1つの起動あたり 5〜10 秒と、非対話 CLI 1往復分のトークンが増える。利用不能な席を卓へ載せる
コスト（今回は席1つが丸ごと無駄になり、親の手動復旧を要した）と比べて妥当と判断した。

## 3. 実測

```
$ node experiments/seat-model-liveness-repro.mjs
  ok: live で使えない claude model は seated 成功にならない
  ok: 落ちる時は tmux を触らない（動いている旧席を殺さない）
  ok: live で使えない codex model も seated 成功にならない
  ok: 応答する model では preflight を通り、起動シーケンスへ進む
seat-model-liveness repro: 4/4 green
```

harness の stub は「**対話起動は成功して画面にはバナーが出るが、非対話入口だけ失敗する**」という、
実際に踏んだ形を再現する（画面は正常・実応答は不能）。

### 測定器を先に疑った（決定60）

preflight ブロックを削った欠陥版で harness を回すと、check 1 が
`Expected "actual" to be strictly unequal to: 0`（＝launch-seat が rc=0 で成功扱い）で落ちる。
復元すると 4/4 green に戻る。つまりこの harness は当該欠陥そのものを見ている。

実装中に踏んだ罠も1つ記録する: `set -e` の下で失敗した子プロセスを素の `wait` で待つと、
rc を受け取る前に script ごと死ぬ（stderr も出ない）。`if wait "$pid"; then …; else rc=$?; fi` の形で受ける。
