# f5 seat-usage.mjs の pane 判定が process 停止状態を見ない

## 何を作ったか

`skill/scripts/seat-usage.mjs` に2関数を追加した。

- `tmuxPanePid(socket, target)`: `tmux list-panes -F '#{pane_pid}'` で pane 内 CLI プロセスの pid
  を読む。
- `isPaneProcessStopped(panePid)`: `ps -o pid=,ppid=,stat= -A` を全走査し、対象 pid またはその
  直接の子（shell の foreground job）の stat 先頭が `T`（stopped）かを見る。

`skill/scripts/seat-status-bridge.mjs` の `readSeat` を変更し、`classifyPaneTail` の結果が
`idle` の時だけ `isPaneProcessStopped` を追加で見るようにした。stopped なら既存の4値契約
（busy/blocked/dead/idle）を壊さないよう `dead` として報告する（room UI 側の型を増やさない
判断）。冒頭の判定ロジックコメントと `dead` の定義も更新した。

## どう確認したか

`experiments/seat-stopped-process-repro.mjs`（新規）を実 tmux セッションで走らせた。
launch-seat.sh と同じ形（シェルでセッションを作り `send-keys` でコマンドを送る。直接
`new-session ... sleep 100` で exec すると pane_pid=sleep のフラットな形になり実運用と違う
挙動になるため、shell 経由へ合わせた——1回目の実行はこの違いで FAIL した）。

```
$ node experiments/seat-stopped-process-repro.mjs
  pass  pane_pid が取得できる
  pass  running中は isPaneProcessStopped=false
  pass  running中の画面は idle 風（sleepは何も出力しない）
  pass  shellの子(sleep job)が見つかる
  pass  SIGSTOP後もtmux paneは生きている(pane_dead=0)
  pass  SIGSTOP後も画面はidle風のまま（欠陥の核心: classifyPaneTailだけではidleと誤判定する）
  pass  SIGSTOP後はisPaneProcessStopped=true（本修正の検出）
  pass  SIGCONT後はisPaneProcessStopped=false（解除も検出できる）
seat stopped-process repro: green
```

「SIGSTOP後も画面はidle風のまま」の項目は、`classifyPaneTail` 単体（既存実装、無変更）が実際に
`idle` を返すことを直接確認しており、修正前の欠陥（stopped を idle と誤判定する）の負例になって
いる。

既存の関連 harness の回帰も確認した:

```
$ node experiments/seat-usage-repro.mjs        # 9/9 green
$ node experiments/seat-socket-discovery-repro.mjs  # 7/7 green
$ node experiments/seat-status-socket-repro.mjs     # 4/4 green
$ node experiments/seat-status-blocked-repro.mjs    # 7/7 green
```

## 監査結果1（suzune, room[94]）: 欠陥1件・修正済み

`seat-stopped-process-repro.mjs` は `tmuxPanePid`/`isPaneProcessStopped` という**部品**までしか
測っておらず、room が実際に消費する経路（`readSeat` が出す status）を素通りしていた。
`readSeat` の override（`tentativeStatus === 'idle' && isPaneProcessStopped(...) ? 'dead' : ...`）
を削っても既存 harness 5本が全部 green のままだった（suzune 実測）。

修正: `experiments/seat-stopped-status-e2e-repro.mjs`（新規）を追加した。実 room server
（fixture, `room/server.mjs` を子プロセス起動）＋実 tmux pane（`send-keys` で shell 経由）＋
`seat-status-bridge.mjs --once` を実際に走らせ、**room へ POST された status** を読み返して
確認する。

```
$ node experiments/seat-stopped-status-e2e-repro.mjs
  pass  fixture room server が起動する
  pass  shellの子(sleep job)が見つかる
  pass  running中はroomへidleが送られる
  pass  SIGSTOP後はroomへdeadが送られる（idleのまま送らない）
seat stopped-status e2e repro: green
```

負例（override を一時的に削った mutation 版で実測。直後に復元し `git status` で差分なしを確認）:

```
  FAIL  SIGSTOP後はroomへdeadが送られる（idleのまま送らない） — status=idle
seat stopped-status e2e repro: RED
exit=1
```

これで「readSeat の override を消せば e2e harness が落ちる」ことを機械的に固定した。

申し送り（suzune, 欠陥ではない・対応不要）: ①`dead` の消費側は room Web UI のチップ表示だけで
破壊的動作は無い（stopped→deadへ倒す判断は妥当）②override が効くのは
`tentativeStatus === 'idle'` の時だけなので、`esc to interrupt` を残したまま停止した席は busy
のまま固まるが、実測の局面（前面プロセス停止でshellがプロンプトを描き直す）では idle 風になり
今回の受入範囲では問題にならない ③`ps -A` の全列挙は idle と読めた時だけ走るので tick あたりの
負荷は妥当。

`node --check` で `seat-usage.mjs`・`seat-status-bridge.mjs` の構文も確認済み。

## 受入条件

- pane 文字列判定に加えて対象 pid の実際の `ps` state を組み合わせた判定へ直す — 確認済み。
- 既存の busy/blocked/idle 判定・呼び出し元（`seat-status-bridge.mjs`）を壊さない — 既存4値の
  contract を維持（新しい status 値を追加せず `dead` へ倒す）、既存 harness 4本の回帰確認済み。
