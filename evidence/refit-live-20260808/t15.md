## 実装前に、設計メモの判定パターンを実物で否定した

設計メモは「Claude 席＝`Cogitating` 等の実行中表示」で照合しろと書いていた。**実装前に実席の pane を採ったら、そのままでは動かない**ことが分かった（読み取りのみ・席へは1バイトも送っていない）。

```
peer-haruka esc=1 Coalescing…    peer-mio  esc=1 Fermenting…
peer-ichika esc=1 Effecting…     peer-suzu esc=1 Symbioting…
peer-kotoha esc=1 Gallivanting…  peer-rin  esc=1 Working (…)   ← Codex 席
peer-hinata esc=0 （スピナー無し）
```

- **実行中の動名詞は毎回変わる**。`Cogitating` はこの時点で**1席も出していない**——語で照合すると**全席を idle と判定して、画面が嘘をつく**
- **`esc to interrupt` が両 vendor 共通で効く**。busy な6席すべてに在り、唯一の非 busy にだけ無い。Claude 席のステータス行にも Codex 席の `Working (…)` にも入るので**vendor 分岐が要らない**

bell が**設計メモの上書きとして受理**（room [273]）。**測定器を先に用意していなければ、負のコントロール（bridge 停止で unknown へ落ちるか）は通ったのに busy 判定が全席で外れる**——通っても意味を持たない green になっていた。

## 層① bridge（`f3ee8a1`）

- 判定: **busy = pane 末尾に `esc to interrupt`**／**dead = セッション無し・`pane_dead=1`**／idle = 生きていて busy でない
- 監視対象は **room の members に居る席だけ**。`tmux` の `peer-*` を全部拾うと、同じマシンの**別の卓を晒す**
- 送信は**変化時＋変化が無くても心拍**。変化時だけだと **bridge の死と無変化を server が区別できない**（決定58 の liveness / cursor 分離の適用。bell が設計メモより強いとして受理）
- 生死は ADR 0157（pid 記録・起動時に死んだ記録を掃除・`--stop`）

| 実測 | 結果 |
| --- | --- |
| busy / dead 判定 | 実席6席で `haruka/mio/kotoha/ichika/rin → busy`・`bell → dead`（bell に tmux 席は無い＝正しい） |
| CPU 負荷（受入の1行） | 13秒稼働で **%CPU 0.0・RSS 58MB**（5秒間隔×6席の `capture-pane`）＝**無視できる** |
| 二重起動 | pid 記録が生きていれば拒否 |
| `--stop` | 停止・pid 削除・rc=0／起動記録が無い時も rc=0（撤去済みを失敗にしない） |
| 本番 room への影響 | **発言数 281→281（増分0）** |

### 事故を1件起こして、直した

**最初の試走で本番 room へ「◯◯ が参加した」を6件撒き、全席を起こした**（room [274]-[279]）。当時の `POST /members` は既存メンバーでも system 発言を出す作りで、**その挙動は同じ日に私が t3 で調べて証跡と SKILL.md に書いていた**。「知っている」と「設計に効かせている」は別だった。

対処は**送信の前に `GET /members` で server が `status` を保持する版かを判定し、未対応なら1バイトも投げない**。当初は「投げてから読み返して警告」にしていたが、**読み返しは投げた後なので撒いてしまってからでは遅い**——判定を送信の前へ移したのが直しの本体（再実行して**発言数の増分0**を実測）。

なお **server 側の恒久対処（system 発言は本当に新規の時だけ）は haruka の t14 で入った**。私が room で要求し、mio が「2つの task が同じ地雷の上に建っている」と整理し、先に入る t14 が持った形。

**`--stop` が生の traceback を吐いていた**のも途中で潰した（SIGTERM handler が先に pid を消し、停止側の `unlinkSync` が ENOENT）。止まってはいたが「何が起きたか分からない失敗」を出していた。

## 層③ UI（`88d28a6` へ同乗）

- チップに稼働状態の点: `busy`=動作色／`idle`=待機色／`dead`=警告色／**`unknown`=中空の輪**。tooltip にも「状態 作業中／待機／停止／**不明（報告が途絶えている）**」
- **鮮度**: `status_at` が **90秒**（bridge の心拍30秒の3倍）より古ければ **`unknown` へ落とす**。**古い状態を出し続けるのがいちばん悪い**
- **状態を一度も名乗っていない席は点そのものを出さない**（空欄を「不明」として見せない）
- 色は light/dark のトークンで持ち替え（`--busy`/`--idle`/`--dead`）

**CDP で5パターンを実測**（使い捨て server・本番不接触）:

| 席 | 与えた状態 | 描画 |
| --- | --- | --- |
| ことは | `busy`・いま | `dot=busy` 緑 |
| いちか | `dead`・いま | `dot=dead` 赤 |
| すず | `idle`・いま | `dot=idle` 薄 |
| **みお** | **`busy`・5時間半前** | **`dot=unknown`・中空の輪**（＝負のコントロール。**古い報告を緑のまま出さない**） |
| はるか | 状態なし | **点そのものが無い** |

console error 0。**この受入の本体は「みお」**——新鮮な busy が緑になるのは当たり前で、**古い報告を新鮮な色で出さないこと**が要件だから。

## 途中で見つけた別の欠陥（報告済み・私の task 外）

**HEAD の配信 client JS が構文エラーで丸ごと死んでいた**（t14 `eb15aaa` 由来）。UI テンプレートは JS の template literal の中に client JS を書く面なので、`'\n'` と書くと**サーバー側の評価で実改行に化けて文字列が閉じない**。`node --check room/server.mjs` は通るので**サーバー側の構文検査では原理的に捕まらない**。私と ichika が別経路で同じ場所を指し、haruka が `88d28a6` で修正。**私も t15 の変更で同じ罠を1回踏んでいる**——同じファイルで同じ日に2人が落ちたので、**個人の不注意ではなく面の性質**。

## 付随: 再現ハーネスのポート穴（自分の成果物の欠陥）

`experiments/member-repost-noise-repro.mjs` の**既定ポート 8816 が他席の宣言と衝突**し、**他人の server に当たったことに気づけない**作りだった（haruka が横断回帰確認で発見・room [314]）。3点を直した:

1. **固定の既定ポートを持たない**（空きポートを OS から取る）
2. **`stdio` を捨てず起動失敗を握り潰さない**（`EADDRINUSE` が見える）
3. **自分の子がそのポートを掴んだことを、子の起動ログで確かめる**——**応答が返ることは「自分の子に繋がった」証明にならない**

| 実測 | 結果 |
| --- | --- |
| 正（ポート自動選択） | 4項目すべて pass |
| 負のコントロール（`eb15aaa~1`） | **「発言数 1 → 4（3件撒いた）」を検出** |
| **他人の server が居るポートを指定** | **rc=2 で中止**し、`EADDRINUSE` と「子が port を掴めていない」を表示 |

**最初に入れた「room が空か」の判定では不十分だった**——他人の server にもこの room 名は無いので空に見え、**全項目 pass を読みかけた**。確実なのは「私の子が `on :<port>` を出したか」だけ。
