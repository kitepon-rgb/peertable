## `--parallel-frontier` の条件（room [17] の申し送りを訂正した）

つむぎが [17] と `evidence/t1.md` 38行目で「independence が未 compile の plan では弾かれる／実運用の最初の1コマンドが
必ずコケる」と申し送ったが、**これは誤診断**である。訂正の出典は つむぎ自身の自認 room [21]（本人の要請により明記）。

実コード（`Lattice src/todo-cli.mjs:692-714`）が持つ条件は2つだけ:

- `parallelFrontier && !targetReady` → `PARALLEL_DISPATCH_INVALID / parallel_frontier_not_applicable`
  （`targetReady` ＝ 取ろうとしている task が `next_ready` に居るか。independence の compile 状態は条件に入っていない）
- `targetReady && active_set.length === 0 && next_ready.length > 1 && フラグも理由も無い`
  → `PARALLEL_DISPATCH_REQUIRED / parallel_frontier_requires_declaration`

反証となる実測（いずれも independence 未 compile のまま）:

- t3 の start（journal seq 1）: ready 2件・active 空で **`--parallel-frontier` 付きが成功**
- t2 の start（journal seq 5）: ready 1件で **フラグ付きが成功**、advisory は `coverage: "missing"`（＝未 compile）
- つむぎが踏んだのは、**私が seq 1 で着手済みの t3** へ後からフラグを付けたケース（`evidence/t1.md` 38行目の実コマンドが
  `--task t3 --parallel-frontier` であることから特定）。t1 が素の start で通ったのは、その時 active に t3 が居て
  contested にならなかったため（つむぎが [21] で 705-708行を読んで補足）

`evidence/t1.md` は digest 束縛済みで書き換えられないため、訂正の事実は本証跡が持つ。
t1 の done は取り消していない——t1 の受入条件は単独円卓モードの実装であり、当該行は受入条件外の申し送りだったため
（この判断は room [20][21] で合意済み）。罠DB の既存エントリも同じ誤りを持っており、つむぎが卓の外で訂正する。
