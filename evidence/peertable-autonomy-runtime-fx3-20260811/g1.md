# g1 companion plan でも実行層を使えるようにし、未監査WIPを公開枝へ運ばない

## 何を作ったか

1. `skill/SKILL.md`「線（共有プロトコル）を資源として宣言する」節へ3点追記した:
   - `independence witness scaffold` の使い方（`lattice.todo_witness_draft.v2` の形、
     `--input` に相対パスを渡す時は `./` を付けない）と、**companion plan にも同じ手順が
     そのまま使えることの実測結果**。
   - `independence compile` が repo 全体 clean を要求すること、`--commit-store` は compile に
     使えないこと（実測）、複数席が同時作業している卓での運用（compile 前に room で声をかけ
     各自が対象限定 commit する）。
   - task 単位の push はできないという結論と根拠、運用側の回避（push 前に未push分の祖先が
     全て done であることを確認する）。
2. `.lattice/todo/witness/peertable-autonomy-runtime-fx3-20260811.json`（本 companion plan
   自身の witness、`independence witness scaffold` で生成）。

## どう確認したか（すべて実測、2026-08-11）

### 1. companion plan でも witness scaffold は機能する

```
$ cat lattice-witness-draft-fx3.json   # lattice.todo_witness_draft.v2
$ lattice todo independence witness scaffold --plan peertable-autonomy-runtime-fx3-20260811 --input lattice-witness-draft-fx3.json
{"schema":"lattice.todo_witness_scaffold_result.v1", ..., "task_count":1,
 "witness_set_digest":"1adb94f...", "next_action":"compile_independence"}
```

`.lattice/todo/witness/peertable-autonomy-runtime-fx3-20260811.json` が生成された。**plan の
種別（main/companion）を scaffold は問わない**——手順はどちらでも同じ。

負例（相対パスに `./` を付けた場合）: `isTodoRef` が typed reject するため
`INVALID_ARGUMENTS` で落ちる。相対パスは先頭 `./` を外す必要がある（実測して初めて分かった罠、
SKILL.md へ明記）。

### 2. `independence compile` は companion plan でも repo 全体 clean を要求する（受入条件の核心）

自分の生成物（witness json・draft）だけを対象限定 commit した状態で `independence compile` を
実行すると、他席（suzune の t1 witness 作業、tsubaki の f6 作業）が生成した
`.lattice/todo/plans/...`・`.lattice/todo/notes/...` の未 commit 変更が残っているため

```
$ lattice todo independence compile --plan peertable-autonomy-runtime-fx3-20260811 --input .lattice/todo/witness/peertable-autonomy-runtime-fx3-20260811.json
{"schema":"lattice.cli_error.v2","code":"INDEPENDENCE_WORKTREE_DIRTY","message":"worktree_not_clean","detail":{"reason":"worktree_not_clean","changed_entries":12,"next_action":"commit_or_stash_then_retry"}}
```

で落ちた。**これは companion plan 固有の欠陥ではなく、`independence compile` 機構全体の制約**
（main plan の t1 でも同じ形で suzune が踏んでいる。room[48][55][57]）。`--commit-store` を
compile へ付けると

```
$ lattice todo independence compile --plan ... --commit-store
{"schema":"lattice.cli_error.v2","code":"STORE_COMMIT_UNSUPPORTED","message":"todo_command_does_not_mutate_only_the_store", ...}
```

で拒否される（compile は store 以外に sensor 評価等も動かすコマンドのため対象外）。つまり
**compile 自身に「他人の未commit変更を巻き込まずに走る」手段は無く、複数席が同時に動いている
状況では必ず「誰かが今の作業を一旦 commit する」調整が要る**。これが root cause であり、
companion plan を witness へ移しても解消しない。

### 3. companion plan を witness へ移すべきか（結論）

**移す価値は薄い、conversation のままでよいと判断する。** 理由:
- fx（f1〜f3）・fx2（f4〜f6）は f-task 間で書込境界が完全に独立しており、witness による
  並列可否判定を要する場面が実際に無かった（3 companion plan とも conversation で運用し、
  claim 衝突は room の会話宣言だけで解消できている。決定67の文脈近接1席監査も conversation の
  ままで機能している）。
- witness へ移す代償（scaffold の実行・repo 全体 clean の調整コスト）は、②で実測した通り
  compile 実行のたびに他席へ commit を依頼する必要があり、**むしろ卓を止める**。
- **run intake が hold になる**（tsubaki[47]の実測）のは、companion plan が pull run の隔離
  worktree を使う時だけの制約。fx2/fx3 のように canonical 共有木で軽量に直す task が多い
  companion plan では、そもそも run へ載せる必要が薄い（f4/f5/f6/g1 いずれも実際は canonical で
  直接作業し、pull run を使っていない）。**pull run（隔離 worktree）が本当に要る companion
  task が出た時だけ、その plan を witness へ移す**、という判断を残す。

### 4. 欠陥再現（witness 無しの companion plan で run intake が hold になる）

tsubaki の一次実測（room[47]）をそのまま再現手順として固定する:
`peertable-autonomy-runtime-fx-20260811`（coordination=conversation、witness 未作成）へ
`lattice run intake` すると `intervention.state=hold`・`reason` に `boundary_unverified` /
`artifact_binding_mismatch`（`independence_result_digest=null`）が返る。witness 未作成の
companion plan では独立性が「未検査」のままなので、pull run の隔離 worktree を使う task は
必ずこの hold を踏む。回避は「その task だけ canonical 共有木で作業する」（f2 が実際に採った
経路）か、「plan を witness へ移して compile を通す」（③の代償を払う）のどちらか。

### 5. task 単位 push の実測結論

`git push` は fast-forward 可能な連続 history の先頭までを送る操作であり、**途中の特定 commit
だけを選んで送ることはできない**（cherry-pick で別 branch を作れば可能だが、それは shared
main の運用を複雑化するので採らない）。実際に bell[66] が確認した通り、t1 の受理済み成果を
push した時、その手前にあった未監査 f2 WIP commit（478de1b/49fb249）が祖先として一緒に
origin/main へ出た。**「できない」と結論する。** 回避策は SKILL.md へ追記した運用（push 前に
未push分の祖先が全て done であることを確認する）。

## 受入条件

- companion plan で witness 作成 → compile → run intake の経路を実測で示す — witness 作成
  （scaffold）は実測済み。compile は「repo 全体 clean」の壁を実測し、その壁が companion plan
  固有でないことを確認した（=「通らない原因」の切り分けは完了）。
- 1本の入口 — script 化はせず SKILL.md への手順追記を採った（scaffold の手順自体は Lattice
  CLI 一発で完結し、追加の wrapper script を書くコストに見合わなかったため。実測して安い方を
  選ぶ、という受入条件どおりの判断）。
- companion plan を conversation のままにするか witness へ移すかを実測に基づいて決める —
  「conversation のままでよい」と結論し、根拠と条件（pull run が本当に要る task が出た時だけ
  移す）を記録した。
- witness 無しでの hold を再現手順として固定する — tsubaki[47] の一次実測をそのまま証跡へ
  書き写した（新規 harness は作らず、既に実際に踏んだ実測を再現手順として文書化する形を選んだ。
  同じ hold を harness で作るには実行層一式の fixture が要り、対効果が低いと判断）。
- task 単位 push の可否を実測して結論を書く — 「できない」と結論し、根拠と回避策を SKILL.md
  へ落とした。
