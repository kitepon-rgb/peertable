## 何を落とし、何を残したか

**装置が席を選んで仕事を配る向きを撤去した。** 落としたのは向きの部品だけで、設備は残している。

### `skill/scripts/run-bridge.mjs`（605行 → 255行）

落とした: `scanOrders` / `dispatch` / `seatBusyState`（idle 選定）/ `[受諾]`『[辞退]』の再配車連鎖 /
`writeReport` / `readReport` / `seatWorkerPid` / `seatOfWorkerPid` / `orderText` / `validOrder` /
`canonical`（work order 契約用）/ SSE 三段（room の発言を機械 parse する必要が消えたため）。

残した: `processFacts` / `stopRecorded`（ADR 0157 の pid 再認証）/ pid 記録 / room 投稿。

**結果、書き込み経路が `.team/run-bridge.json`（自分の pid 記録）1つだけになった。**
spool にも run store にも1バイトも書かない。**読み取りだけの中継**である。

新しい役目は2つ:
- `run list --json` で `selection: 'pull'` の run を拾い、`run observe` を10秒ごとに read-only で叩いて、
  **変化した時だけ** `[run] <run-id> intake=[…] accepted=[…] hold=[…] closed=…` を room へ
- `intervention.state === 'hold'` になった intake を、**その作業を始めた席**（`intake.actor.agent`）宛へ返す

`intake.actor` は r1 の consumer 検算で私が要求して公開してもらった欄で（room [868]→[869]）、
**これが無いと bridge が Todo journal の内部構造を別読みすることになっていた。**

### `skill/scripts/launch-seat.sh`

席が自分の pid を知る経路を新設した。Lattice の `run intake attach` は expected identity を要求し、
**pid を推定しない**ので、席側に供給源が要る。

- **起動前**に同名の自分の記録だけ削除（ADR 0157: 全席が必ず通る一点に掃除を置く。teardown や
  人が叩くコマンドに置くと誰も叩かず溜まる。`peer-*` の一括削除はしない——別卓を巻き込む）
- **着席確認の後**に `.team/seats/<name>.json` を canonical JSON・0600・一時file→fsync→rename で置く
- 6欄 `{name, session, pid, started_identity, argv_digest, recorded_at}` は
  **`lattice.pull_worker_attach_input.v1` の exact 集合から `schema` を除いたものと一致する**——
  席は読んで `schema` を被せるだけで attach input になる（変換も digest 計算も要らない）
- pid は **pane の子で `pid===pgid`** のもの。**1件でなければ記録しない**（`run-bridge` の
  `seatWorkerPid` と同じ規律。推測で1つ選ばない）
- 取れなければ**黙らず stderr**。記録が無ければ attach できず、装置の介入が協調 hold のままになる

**raw argv を持たせない。** Codex 席の起動 argv には `PEERTABLE_POST_TOKEN` が載るので、
保存すれば秘密の複製になる（mio の監査指摘・room [833]）。持つのは SHA-256 digest だけ。

### `skill/templates/member.md` / `skill/SKILL.md`

「配車で来た仕事」→「Lattice の実行層へ自分の着手を載せる（pull 型）」へ向きごと書き換え。
手順は `todo start` → `run intake` → `intervention` 判定 → `attach` → 作業 → `todo done` → `accept`。

- **1席1 active intake を明文化した。** 席は1つの process なので、2本 intake すると片方の hold が
  もう片方を巻き込み、制御の粒度が壊れる（akari [817]）
- **worktree の記述の誤りを直した。** 旧文は「supervisor 終了時に畳まれる」と書いていたが、
  実際に畳むのは `run abandon` だけである（`removeScriptedWorktrees` の呼び出しは1箇所）。
  **これは私が t5 で一度直した節で、直した先も実物と違っていた**——`abandon` 分岐のコメントを読んで
  「close ではない」までは掴み、「では何なら畳むのか」を確かめずに推定で書いた
- 配車語（配車・`[受諾]`・`[辞退]`・work order・managed run）は member.md から**0件**になった。
  SKILL.md に残る2箇所は「撤回された」と説明している本文で、手順ではない

## どう確かめたか

### 実測（すべて実物・実 process）

```
① seat record を実際に作れる（私の席）
   pane_pid → 子で pid===pgid が 1件だけ確定 → 6欄・0600・224 bytes
   started_identity 24字 / argv_digest 64字 / token 文字列なし

② 負の対照: token が argv に載っている席で作っても漏れない
   peer-akari（Codex席・argv に PEERTABLE_POST_TOKEN が1箇所ある席）で生成
   → 記録に PEERTABLE_POST_TOKEN なし / mcp_servers なし / 全長 220 bytes
   **私の Claude 席（argv に token が無い）だけで試しても、この性質は確かめられない**

③ 旧 command line を typed に拒否する
   node run-bridge.mjs <proj> <spool> <席名>  → exit 1 / RUN_BRIDGE_ARGS_INVALID

④ ③の時、動いているブリッジを殺さない
   拒否前 pid 2580 → 拒否後も pid 2580 が生存・記録も無傷

⑤ --stop で止まる
   exit 0 / pid 2580 不在 / .team/run-bridge.json も消える

⑥ 起動して pull run を観測する
   bridge start … （配車はしない・観測と中継だけ）→ `pull run 0 件を観測中`
   記録に token 文字列なし

⑦ 後始末: node で run-bridge を走らせている process 0 件
```

### ④は自分の実装の欠陥を自分で踏んで直したものである

最初の版は `stopRecorded()` を引数検査より**先**に呼んでいた（旧版からの順序をそのまま残した）。
その結果、**旧 command line で叩くと「動いているブリッジを殺してから起動に失敗する」**——
正典が旧形式を載せていた期間があるので、これは実際に起きる。検査を停止より前へ移した。
`--stop` は検査を通さない（止めるだけの呼び出しに `--lattice` は要らない）。

**気づいたのは、③の負の対照を実際に走らせたからである。** ログの1行目に
`前のブリッジを停止した（pid 72696）` が出ていた。**拒否されたことだけを見ていたら見落としていた。**

### 測定器についての記録

- ③の1回目、`node … | head -3` で見て `exit=0` と読んだ。**それは head の終了コードで、
  測りたいものではない。** パイプを外して測り直し、`exit=1` を確認した
- ⑦の1回目、`ps -eo pid,command | grep run-bridge` が**自分の shell の command line を拾って**
  1件と出た。node の process だけを数える形へ直して 0 件を確認した

どちらも今日の卓で既に踏んでいる型で、**同じ罠に同じ日に2回落ちている。**
