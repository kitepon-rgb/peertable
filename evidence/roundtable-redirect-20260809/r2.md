## 何を落とし、何を残したか

**装置が席を選んで仕事を配る向きを撤去した。** 落としたのは向きの部品だけで、設備は残している。

### `skill/scripts/run-bridge.mjs`（605行 → 255行）

落とした: `scanOrders` / `dispatch` / `seatBusyState`（idle 選定）/ `[受諾]`『[辞退]』の再配車連鎖 /
`writeReport` / `readReport` / `seatWorkerPid` / `seatOfWorkerPid` / `orderText` / `validOrder` /
`canonical`（work order 契約用）/ SSE 三段（room の発言を機械 parse する必要が消えたため）。

**結果、書き込み経路が `.team/run-bridge.json`（自分の pid 記録）1つだけになった。**
spool にも run store にも1バイトも書かない。**読み取りだけの中継**である。

新しい役目は2つ:
- `run list --json` で `selection: 'pull'` の run を拾い、`run observe` を10秒ごとに read-only で叩いて、
  **変化した時だけ** `[run] <run-id> intake=[…] accepted=[…] hold=[…] closed=…` を room へ
- `intervention.state === 'hold'` になった intake を、**その作業を始めた席**（`intake.actor.agent`）宛へ返す

`intake.actor` は r1 の consumer 検算で私が要求して公開してもらった欄で（room [868]→[869]）、
**これが無いと bridge が Todo journal の内部構造を別読みすることになっていた。**

### `skill/scripts/launch-seat.sh`

席が自分の pid を知る経路を新設した。Lattice の `run intake attach` は expected identity を要求し、
**pid を推定しない**ので、席側に供給源が要る。

- **起動前**に同名の自分の記録だけ削除（ADR 0157: 全席が必ず通る一点に掃除を置く。teardown や
  人が叩くコマンドに置くと誰も叩かず溜まる。`peer-*` の一括削除はしない——別卓を巻き込む）
- **着席確認の後**に `.team/seats/<name>.json` を canonical JSON・0600・一時file→fsync→rename で置く
- 6欄 `{name, session, pid, started_identity, argv_digest, recorded_at}` は
  **`lattice.pull_worker_attach_input.v1` の exact 集合から `schema` を除いたものと一致する**——
  席は読んで `schema` を被せるだけで attach input になる（変換も digest 計算も要らない）
- pid は **pane の子で `pid===pgid`** のもの。**1件でなければ記録しない**（`run-bridge` の
  `seatWorkerPid` と同じ規律。推測で1つ選ばない）
- 取れなければ**黙らず stderr**。記録が無ければ attach できず、装置の介入が協調 hold のままになる

**raw argv を持たせない。** Codex 席の起動 argv には `PEERTABLE_POST_TOKEN` が載るので、
保存すれば秘密の複製になる（mio の監査指摘・room [833]）。持つのは SHA-256 digest だけ。

手順は `todo start` → `run intake` → `intervention` 判定 → `attach` → 作業 → `todo done` → `accept`。

## teardown が「CLI 失敗」を「active run なし」へ化かしていた（suzune [948]）

**私が書いた pipeline が、いちばん避けたい壊れ方をしていた。**
```
run_refs=$( … "$lattice_cli" run list --json 2>&1 | python3 -c '…listed.get("active_runs", [])…' )
```
`cmd | python3` は **pipeline の rc が python のもの**になる。CLI が rc=2 で typed error JSON を返しても、
parser が `active_runs` 欠落を空配列として飲み、`skip run landing（active runなし）` で**沈黙する。**
**着地の見落としが、そのまま「確認済み」に見える。**

直した形:
```
1. CLI の出力と rc を**先に単独で取る**（`run_list_json=$(…) || run_list_rc=$?`）
2. rc≠0 なら miss（出力の先頭200字を添える）
3. 成功した時だけ parser へ渡す。parser は **schema=lattice.run_list.v1 と active_runs 配列を要求**し、
   満たさなければ非ゼロで落ちる（typed error JSON も別 schema も黙って空扱いにしない）
```
**4負側 + 正側を実測した**（parser を取り出して直接叩いた）:
```
① typed error JSON  → 「run list の schema が違う: lattice.cli_error.v2」  rc=1
② JSON でない        → 「run list がJSONでない: Expecting value…」          rc=1
③ schema 違い        → 「run list の schema が違う: lattice.other.v1」      rc=1
④ active_runs 非配列 → 「run list に active_runs 配列が無い」               rc=1
⑤ 正側（実 CLI）      → CLI rc=0 / parser rc=0 / 5 件抽出
```

**これは今日3回目の「`|` の後ろの rc を読んでいた」である。** 私は同じ証跡の中で
「`| head` の exit code を読んだ」を測定器の不備として書いた直後に、**製品コードで同じ形を書いた。**
測定器で気をつけると決めたことが、実装には移っていなかった。

## 直した parser と、exact 抽出での実測（正2＋負5）

- f-string の中でバックスラッシュ付き引用符を使わない。**値を先に変数へ取り出して名前だけ置く**
- **entry を filter で捨てない**（suzune [956]）。1件でも読めない entry があれば active な run を
  落として「なし」に見せる。全件が object かつ非空 `run_ref` 文字列であることを要求し、
  満たさなければ非ゼロ。**外部 versioned JSON の境界で fallback しない**

`teardown.sh` から **un-escape せずに** 抜いた本文（32行）を実 Python へ渡した。
`\"` は **実行文中 0 件**（comment に1件だけ残る——その1件が今回の欠陥の説明である）。
**本証拠は grep の件数ではなく、下の実 Python の rc である**（suzune [974]・mio [975] の指摘で
「残り 0 件」という書き方を直した。数え方が甘いと、また「測ったつもり」になる）:
```
① typed error JSON        rc=1  run list の schema が違う: lattice.cli_error.v2
② JSON でない              rc=1  run list がJSONでない: Expecting value…
③ 別 schema                rc=1  run list の schema が違う: lattice.other.v1
④ active_runs 非配列        rc=1  run list に active_runs 配列が無い: NoneType
⑤ 不正 entry `[{}]`        rc=1  active_runs[0] に run_ref 文字列が無い
⑥ 正側（active 空）         rc=0  0 件
⑦ 正側（実 CLI・Lattice）   rc=0  5 件抽出
```
**⑦は最初 0 件が出た。** peertable の cwd で叩いていたからで（そちらに active run が無い）、
Lattice の cwd で 5 件になった。**「rc=0 だから正側 green」で片付けず、件数まで見て気づいた。**

**`bash -n` は inline Python を検査しない**（akari [958]）。この節の実測が受入証拠であって、
`bash -n OK` はその代わりにならない。

### ① `todo done` が worktree の成果へ到達できなかった（mio [1012]）

**私が member.md へ書いた「`todo done` を打ってから accept」は、pull では実行不能だった。**
```
done.sh:9-15  f="evidence/$PEERTABLE_PLAN/$t.md"  ← **実行 cwd 相対**で読み、その cwd の store へ打つ
canonical で打つ → worktree にしか無い証跡を読めない
worktree で打つ → worktree 側の .lattice/todo を書き、canonical run の accept が見ない
```
**私はこの節を t19（push モデル）の手順から書き写した。** あの時は席が `todo done` を打つ必要が
無かった（bridge が report を書いた）ので、**pull で誰がどこで打つかを考えていなかった。**

`done.sh` へ **`--evidence-from <worktree の絶対path>`** を足した。
**証跡の blob/digest は worktree の file から、`todo done` は canonical の cwd/store へ**、と明示的に分ける。
**canonical へ証跡を別書きして通すのは禁止**（「worktree の中だけ」の契約を破りながら green にする偽装）。

**成立することを実測した**（私が [1015] で「実測していないので断定しない」と書いた仮説の確認）:
```
$ git hash-object -w <worktree/evidence の絶対path>   （canonical の cwd から）
  → cd1283f8…  canonical で cat-file 可・8094 bytes
  worktree file の sha256      6a0be8b401c024db8d490bf0f2bd45ed435aff49353e8c0871a18018c3ce5a08
  書かれた blob の sha256      6a0be8b401c024db8d490bf0f2bd45ed435aff49353e8c0871a18018c3ce5a08  （一致）
```
linked worktree は canonical と object DB を共有するので、**canonical の cwd から worktree の file を
hash-object できる。** evidence verifier は descriptor.path の working tree 実在を見ず、object DB の
blob と digest、読み出し時の `rev-list --all` 到達性を見る（mio が実 repo で確認・[1016]）。

負側を実測した（**store を触る前に落ちる guard だけを叩いた**）:
```
① 相対 path を渡す        rc=1  「--evidence-from は絶対pathでなければならない」
② 存在しない絶対 path     rc=1  「--evidence-from の証跡が存在しない」
③ 値を渡さない            rc=1  「--evidence-from には証跡fileの絶対pathを渡すこと」
```
**②が重要である。** ここで黙って canonical の証跡へ落ちると、「worktree の成果を done した」と
見えるのに実際は別の file を hash することになり、**受理された内容と成果物が食い違う。**

**rc の測り方をまた間違えた。** 最初 `cmd | head -1` の後に `PIPESTATUS[0]` を読もうとして空になり、
pipe を外して測り直した。**今日4回目**。`|` を書いたら rc がどちらのものかを見る、が身に付いていない。

### ②' pull run の生成手順（r1 の空 close 確定後に書いた）

**私が作った `r2-probe-1` も実際に閉じて active から消えた。** 出口が確定したので手順を書いた。

`member.md` / `SKILL.md` へ:
```
0. run list --json で同 plan の active pull run（selection:"pull"）を確認する
   1件 → 共有する（席ごとに作らない）
   0件 → **room で生成担当を1席決めてから**作る（競争を先に潰すのがいちばん安い）
          run start --selection pull --id <plan>-<一意suffix> --plan <key> --equipment detached-worktree
   RUN_EXISTS → **相手の run を推定しない。** 再 list → active があれば共有、無ければ別の一意 id で作り直す
   複数件 → 止めて room で決める（どれが正かは機械には決められない）
1. 作った席は run_ref を room へ共有する
**これは設備の生成であって配車ではない。** run は intake の入れ物で、中身は空のままである
```
**id に plan key だけの固定値を使わない**ことを明記した——`close` しても run directory は残り、
`run list` は closed を返さないので、**「無いのに `RUN_EXISTS` で作れない」**袋小路に入る。
これは mio [1005] の自己訂正で、**私が [1003] で初案を書き写していた**分もここで取り下げる。
