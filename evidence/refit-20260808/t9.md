# t9 無人席のブラウザ選択ダイアログ停止対処の正典改訂

担当: kotoha / 2026-08-08 / plan `refit-20260808`
対象: `skill/templates/member.md`（席の役割文書）・`skill/SKILL.md`（親の督促手順）。script 変更なし。

## 一次資料（当事者としての記録）

停止したのは私の席で、外から見た観測（`Cogitating…` の経過秒・トークン受信の増加・実画面のバナー）は
haruka・ichika・bell・mio が room に出している。**呼び出した側から見た形**はここにしか無いので、それを書く。

- `claude-in-chrome` の `navigate` が **`Multiple Chrome browsers are connected … none has been selected`** を返し、
  **どれを使うかを人へ聞くまで先へ進めない**状態になった。ツールは「AskUserQuestion で全ブラウザを列挙して聞け」と
  指示してくる＝**設計として人の回答を要求する**
- 私はオーナーへ聞いて macOS 側を選び、そこから復帰した。**解けたのは、聞ける相手が居たから**
- **モーダル固着ではなかった**。卓は当初「ブラウザにモーダルが出て拡張が固まった」と推定していたが、bell が
  実画面を見て否定している（ブロッキングモーダルは無く、2窓が拡張の制御下・デバッグ開始バナーが宙吊り）
- 併せて実測した事実: **`chrome-devtools` MCP も使えなかった**——`The browser is already running for … chrome-profile`
  で起動を拒否される（他が同じ profile を掴んでいる）。**「chrome-devtools MCP を使えば安全」は成り立たない**

## 何を書いたか

### `skill/templates/member.md`（席が読む文書）

- **`claude-in-chrome` をブラウザ検証に使わない。** 拡張経由で実 Chrome を触るため、**接続ブラウザが複数ある時に
  人へ聞くまで返らない**。席には聞く相手が居ないので、**無人の席が踏むと自力で復帰できない**
- 使うのは**自分で起こす headless の Chrome for Testing ＋ CDP**（`--headless=new --remote-debugging-port=<port>
  --user-data-dir=<temp>`）。**拡張に触らないので、選択待ちもモーダル固着も原理的に起きない**。
  `chrome-devtools` MCP は空いていれば可だが、**他席が profile を掴んでいると起動できない**ことまで書いた
- **共有資源（ブラウザ・ポート・常駐 process）を占める前に room へ一言／終わったら pid 直指定で止める**
  （`pkill -f` は他席の同名 process を巻き込む）

### `skill/SKILL.md`（親の督促手順）

既存の「返らない2種（選択待ち／モーダル固着）」の節へ、**無人席の観点と親の手当**を足した。

- **無人の席はどちらの型も自力で解けない**。選択待ちは「人に聞けば解ける」型だが、**席には聞く相手が居ない**
- **親が解く**: `pty_read`（`screen: true`）で画面を見て、選択ダイアログなら `pty_key` で通す
  （`launch-seat.sh` が起動時の既知ダイアログを通すのと同じ手）。モーダル固着だけはオーナーへ回す
- **督促手順の順序**: ①`capture-pane` で実状態 ②ダイアログなら `pty_key` ③解けない型ならオーナー。
  **呼びかけを増やすのは①の前にやらない**（ターン中なら読まれず、遅くなるだけ）

## 設計メモから外した点（申告）

設計メモは (a) を「**`chrome-devtools` MCP 優先**」と書いていたが、**実測でその経路自体が塞がることがある**
（他席が profile を掴んでいると起動を拒否される）。そのまま書くと「優先しろと言われた経路が使えない」で次の人が止まるので、
**自分で起こす headless ＋ CDP を第一に、`chrome-devtools` MCP は空いていれば可**の順で書いた。
今日この卓で実際に通っている経路（ichika が3回・mio が t10 で使用）はこちら。

## 検証の限界（正直に書く）

- **親の `pty_key` による解除は未実測**。今日解けたのは**席の所有者（人）が選択に答えた**経路であって、
  `pty_key` で同じ選択を通せることは確かめていない。根拠は「席の TUI に出ている選択プロンプトであり、
  `launch-seat.sh` が起動時の既知ダイアログを同じ手で通している」という**機構の同一性**まで。
  **次に踏んだ席で実測する価値がある**——手順として書いたが、実測済みとは書いていない
- 文書だけの task なので**欠陥版を落とす形の負のコントロールは取れない**。代わりに
  **書いた内容が実物と一致すること**（`chrome-devtools` MCP が profile 衝突で落ちること・
  headless ＋ CDP 経路が今日3回通っていること）を room の実測報告と突き合わせた

## 派生して見つけたこと（範囲外・room [報告] へ出した）

**今日 template へ入れた規則は、走っている席には届いていない。** 席が読む `.team/roles/member.md` は
setup 時に生成された固定のコピーで、`skill/templates/member.md` を直しても反映されない。実測（grep 件数）:
「この点を見てほしい」「他席の done を監査」「測定器を先に疑う」「Codex 席の作法」「`[claim]` は独立発言」は
**template に有り・この卓の席の文書に無し**。私が t9 で入れた2項は**template と卓のローカル両方**へ入れたが、
他の項目は範囲外なので触っていない。恒久対処は §11 か次 campaign の議題。
