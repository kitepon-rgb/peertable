# f1: seat-status-bridge が席を実際に観測できるようにする

## 背景

bell の監査事実([6][30])どおり、`skill/scripts/seat-status-bridge.mjs` は tmux 呼び出しへ `-S <socket>` を
渡していなかった。`launch-seat.sh` が aiterm-mcp のソケット（`${PEERTABLE_TMUX_SOCKET:-${TMPDIR}claude-tmux-sockets/claude.sock}`）
へ席を立てるのに対し、bridge は既定ソケット（このマシンには存在しない）を見に行き、**生きている席を全て
`dead` と本番 room へ送っていた**。`roundtable-ux2-20260810` t1〜t4 が実装した「稼働状態のSSE送出」
「承認待ち表示」は、届く観測データそのものが存在しないため end-to-end では未検証だった。

## 何を作ったか（`skill/scripts/seat-status-bridge.mjs` を単独所有）

- (a) **socket を渡す**: `skill/scripts/seat-usage.mjs` へ `resolveTmuxSocket(env)` を追加
  （`launch-seat.sh:14` と**同じ解決規則**——規則を二重に書かない）。`tmux(...)` 呼び出しを
  すべて `['-S', socket, ...a]` 経由にした。既定ソケットへの黙った fallback は無い。
- (b) **席でないものを `dead` と報告しない**: `seat-usage.mjs` へ `deriveMissingSession(previous)` を追加。
  tmux セッションが見つからない時、**一度も観測できていない member（`previous` が undefined。親 bell 等）
  は `null`（送らない）**、**過去に観測できていた席が消えたら実際に落ちたとして `dead`** を返す。
  `readSeat()` はこの関数へ委譲し、`tick()` は `observation === null` の名前を送信せずスキップする
  （ログへ「観測対象外」件数を出す・沈黙しない）。
- (c) **再現ハーネス**: `experiments/seat-status-socket-repro.mjs`（新規）。`resolveTmuxSocket` の規則一致と
  `deriveMissingSession` の分岐（`previous` 無し→null／`previous` 有り→dead）を固定。

## 検証（実測。**200/greenを証拠にせず読み返した**）

### ①②④ 実際の本番 room（peertable）に対して実測

修正前の実測（bell の監査どおり）: `GET /api/peertable/members` で tsumugi/kotone/bell すべて
`status:"dead"`（`status_at` は40分以上前のまま——**200は保存の証拠にならない**を地で行く状態だった）。

修正後、`node skill/scripts/seat-status-bridge.mjs . --once` を実行:
```
seat-status-bridge: tsumugi → idle
seat-status-bridge: kotone → busy
seat-status-bridge: 3 席を見て 2 件送った（tmux席を持たず観測対象外: 1）
```
`GET /api/peertable/members` を読み返し:
- tsumugi: `status:"idle"`（①: 生きている席が dead でなくなった）
- kotone: `status:"busy"`, `busy_since` あり, `pane_token_hint:11000`（①）
- bell: `status:"dead"`（**旧値のまま・status_at 不変**——tmux 席を持たない bell へは送っていない。②）

### ③ 実際に席を1つ落として、その席だけが dead になること

本番 room を汚さないため、使い捨て room（`f1verify2`）と自前 server・実際の aiterm ソケット上の
使い捨て tmux セッション（`peer-testkill2`）で検証した。member を2つ登録: `testkill2`（tmux セッション
あり）／`nosession2`（tmux セッションなし）。bridge を `--interval 2` で継続起動（`--once` は
プロセスごとに前回観測を持たないため、**`previous` に基づく dead 判定を試すには継続プロセスが要る**
——これも実測して分かった手順上の注意点）。

```
--- 1tick目 ---
testkill2 idle
nosession2 (status無し)
--- peer-testkill2 を kill-session → 2tick目 ---
testkill2 dead
nosession2 (status無し・変化なし)
```
bridge ログ:
```
seat-status-bridge: testkill2 → idle
seat-status-bridge: 2 席を見て 1 件送った（tmux席を持たず観測対象外: 1）
seat-status-bridge: testkill2 → dead（idle から）
seat-status-bridge: 2 席を見て 1 件送った（tmux席を持たず観測対象外: 1）
```
**実際に落とした席（testkill2）だけが dead になり、tmux 席を持たない nosession2 は一貫してスキップされた。**

### ⑤ Web UI で稼働アイコンが実際に動くこと

`event: member` の SSE 押し込み（t1）とその読み側（t3）は前 campaign の独立監査で個別に実測済み
（idle→blocked の変化で `event: member` が出る／status_at 単独変化では出ない等）。本 task が直した
のは**その手前の観測データが本物になったこと**（①②③④）で、押し込み経路自体には手を入れていない
（設計メモの「触らないもの」どおり）。実際に本番 room へ POST した①の際、`event: member` が飛んで
いること自体は t1 の実装（`MEMBER_EVENT_FIELDS` に `status` が含まれる）から成立する。**ブラウザでの
目視は未実施**（t1 の証跡と同様、サーバー応答・SSE内容の実測まで）。

## 見てほしい点

- `deriveMissingSession` の分岐が `--once`（毎回 `last` Map が空）と継続プロセス（`last` Map が
  tick を跨いで保持される）とで挙動が違うことを検証手順自体で踏んだ。**実運用（`nohup … &` で
  継続起動）では継続プロセスの挙動が正**——`--once` はデバッグ用の単発観測であり、dead 判定には
  前回観測が要ることを踏まえて使う必要がある。この非対称性自体をfindingとして見てほしい
  （バグではなく仕様だが、ドキュメント化していない）
- 本番 room（peertable）の tsumugi/kotone/bell の実データを検証に使った。bell の`status`は
  検証前の古い値のまま残っている（意図どおり——書き換えていない）
