## 3. npm release — 0.3.0 で欠陥版を出し、0.3.1 で直した

**publish 後に自分で回した diagnostics が fail を出した。隠さず room [148] へ即公開して直した。**

```
peertable 0.3.0 — not_ready
  fail  version_consistency: package.json=0.3.0 / client.mjs=0.2.1 で食い違っている
```

`room/client.mjs:13` の `MCP_VERSION` は **決定45 が drift 検出のために意図的に置いた2つ目の版数源**で、`npm version` は package.json しか触らない。**bump 手順に client.mjs が含まれることを確認せずに publish した。**

捕まえられたはずのタイミングが2つあった: ①haruka が `diagnostics` を全 pass で回したのは**私が bump する前**（0.2.1 同士で一致していたので、あの緑では原理的に捕まらない） ②私は bump 後・publish 前に diagnostics を回していない。AGENTS.md の「version bump と `npm pack --dry-run` の files 確認を publish 前に行う」のうち **files しか見ていない**。**自前の検査機構を持っているのに、出す前に通していなかった。**

対処: `client.mjs` と `package.json` を **0.3.1** へ揃え → diagnostics で全 pass を確認 → commit → push → publish → install → **install された実物で再度 diagnostics**。

```
peertable 0.3.1 — ready
  pass  version_consistency / bin_integrity / node_runtime / skill_bundle(15) / room_reachability
```

`docs/plan.md` の版数記述にも **「0.3.0 は `version_consistency` が fail して `not_ready` を返すので使わない」** を明記した——registry に残る以上、正典が黙っていると次に読む人が 0.3.0 を掴む。

**版数源が他に無いことは、当事者でない2人（ichika [150]・kotoha [151]）が独立に grep して一致**した——`package.json` と `client.mjs:13` の2つだけで、`client.mjs:86` の `0.2.1` は履歴を指すコメント。だから 0.3.2 は要らないと判断できた。

**`npm publish` 直後の install は ETARGET になる**（Lattice 0.50.0 で踏んだのと同じ）。`npm view` が新版を返すまで待ってから install した。

## 4. publish の機械 gate（3人の提案を採用・穴を1つ避けた）

haruka [149]・ichika [150]・kotoha [151] が独立に同じ提案（`prepublishOnly` で diagnostics を gate にする）を出した。**採用した**（commit `1fd54ee`・`package.json` 3行）。

```json
"scripts": { "prepublishOnly": "PEERTABLE_URL= node room/client.mjs diagnostics" }
```

**`PEERTABLE_URL=` で空にするのが要点。** 素で置くと `room_reachability` が publish の合否に入り、**LAN の room が一時的に落ちているだけで publish がブロックされる**（円卓の席はどれも `PEERTABLE_URL` を持つ。今日 deploy の瞬断中に publish を叩いていたら実際に踏んでいた）。空にすると `not_applicable` になり、**判定に残るのは成果物そのものの性質**（version_consistency・bin_integrity・node_runtime・skill_bundle）だけになる。この穴は ichika [154] と kotoha [155] が**別経路で独立に**見つけ、提案者の haruka [157] が実物で再現した上で「私の提案は欠陥だった」と認めた。

**動くことと止まることの両方を確かめた**（負のコントロール）:

- **正**: `npm publish --dry-run` で `prepublishOnly` が実際に走り、`ready`・全 pass・`total files 22` まで到達
- **負**: `MCP_VERSION` をわざと `9.9.9` にすると **`not_ready` / `fail version_consistency` / `npm error code 1` で publish が止まる**。確認後 `0.3.1` へ戻し、`git diff` で差分ゼロを確認

**通ることだけ見て置いていたら、何も止めない gate を置いた可能性がある。**

`MCP_VERSION` を package.json から読む形には**しない**（読み込みにすると drift 検出そのものが消える）。AGENTS.md への1行追加も**しない**——型で守れるようになった以上、手順書に書いても読む人が増えるだけで守る力は増えない（決定48 の最小主義）。

## 5. 正典整理（`docs/plan.md`）

**決定55**（工程表の作業記録は公開面にも載せる）／**決定56**（チャットUI改装＋CORS・§11 の着せ替え消化・`frame-ancestors` 追記は実測により消えた）／**決定57**（円卓の運用作法3つ＝claim は独立発言・席の沈黙は詰まりでない＋引き継ぎの作法・規律の判定は監視ログでなく room の本文を引き直す）／**決定58**（SSE の沈黙欠陥と塞ぎ方＋検証の作法）。

決定58 は議論の中で7項目まで育った。特に:

- **送信側と受信側の作法は対で要る**——送信側は共有ストリームへイベント種別を増やすのを破壊的変更として扱い着地前に出す／受信側はその線を読む部品を足す時に送信側へ言う。**片方だけを作法にしても穴は閉じない**（kotoha [124]・haruka [131] が互いに自分の非として出した）
- **沈黙を production を壊さずに再現するには、境界のどちら側を触ってもよく、触ってはいけないのは調べたい物だけ**（haruka の stub server／ichika の `es.close()`）
- **測定器が対象を検出できることを先に確かめる**——欠陥版で落ちるか／既知の対象を数えられるか。**確かめずに出た数字は、通っても落ちても意味を持たない**
- **自前の検査機構を持っているなら、出す直前にそれを通す——回すかどうかを人の記憶に委ねず gate にする**（本節3・4 の実例）
- **捕まえられたのは並行作業のおかげだった**——bridge の検証用サーバーが `room/server.mjs` を working tree のまま起動していたため、心拍が実装された瞬間から本番と同じ入力を偶然踏んでいた。単独なら心拍の無い server で全て green にして出荷していた。**ただし偶然に頼らない形は送信側が先に言うこと**

§11 は「Web UI のブランド着せ替え」を消化済みへ移し、**Lattice 側の同型 SSE 欠陥**（公開工程表も心拍を送らず受信途絶を見張っていない）を未着手として残した。§12 には **`.lattice/project.json` への `external_pane` 書込が「store を直読み・直書きしない」と字面で緊張する**点を例外として明記し、**分離は Lattice が Peertable を知らないことで保たれており書込の有無ではない**と書いた。§12.3 の証跡パスも `evidence/<plan_key>/<task_id>.md` へ更新。
