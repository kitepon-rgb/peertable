# t5 Codex席対応と wakeup-bridge（P4）— haruka

## 何を作ったか

- **`skill/scripts/wakeup-bridge.mjs`（新規）**: Codex 席の起床ブリッジ。room の SSE を購読し、
  その席宛または全員宛の新着（**自分の発言は除く**）を tmux の席へ素送信して起こす。
  2秒ごとに束ねて1回だけ送る（連投で席を何度も起こさない）。
  生死は Lattice ADR 0157 の作法: `.team/wakeup-bridge.json` へ自分の pid を記録し、起動時に前の記録を
  掃除する（死んでいれば消す・生きていれば SIGTERM→SIGKILL）。止まらなければ
  `WAKEUP_BRIDGE_STOP_FAILED`、SSE へ10回連続で繋げなければ `WAKEUP_BRIDGE_UNREACHABLE` で落ちる
- **`skill/scripts/launch-seat.sh`**: Codex の更新案内ダイアログ（`1. Update now`）を「2. Skip」で通す分岐を追加
- **`skill/scripts/teardown.sh`**: `.team/` を消す前にブリッジを停止する
- **`skill/SKILL.md`**: Codex 席の起動手順（stdio MCP の差し方・env 全列挙・モデル slug の注意）と
  起床ブリッジの起動/停止を手順へ。運用知識へ Codex のダイアログ2種と steering の実測を追加。
  不可侵原則へ external_pane の例外を明記（t4 で docs/plan.md へ入れた分の手順書側）
- **`skill/templates/member.md` / `member-standalone.md`**: Codex 席の注記（起床経路・作業中でも割り込む・
  自分の発言では起きない）
- **`room/client.mjs`**: `skill_bundle` 診断の必須ファイルへ `scripts/wakeup-bridge.mjs` を追加
- **`docs/plan.md`**: 決定54

## どう確認したか（すべて実機）

1. **Codex 席が円卓の会話へ参加した**: scratch project（単独モード・room `t5probe`）へ
   `launch-seat.sh <project> codexseat gpt-5.6-sol codex` で着席 →
   指示に応じて `room.post` を呼び、`codexseat → all: コデックス席、着任した` が room に載った
2. **busy 中の素送信（steering）が通った**——これが計画の第一候補で、通ったので idle 待ちは実装しない。
   席が `Working (… • esc to interrupt)` の状態で割り込みを送ると、その文言は**同じターンの中で読まれ**、
   指示どおり `codexseat → all: 割り込みを受け取った` を投稿した
3. **ブリッジの端から端まで**: ブリッジ起動 → 親が room へ投稿 → ログに
   `起こした: codexseat ← 1 件（最新 seq 5）` → 席の画面に
   `room に新着あり（bell → all）。read_unread で読むこと。` が入り、席が `room.read_unread` を呼んで
   `codexseat → all: ブリッジで起きた` を投稿した
4. **自分の発言では起きない**: 席自身の投稿（seq 6）でログに「起こした」行が増えないことを確認
5. **他人宛の DM では起きない**: `to: someoneelse` の投稿を流してもログに「起こした」行が増えない
6. **停止と掃除**: `wakeup-bridge.mjs <project> --stop` で `前のブリッジを停止した（pid …）` を出して
   process が消え、記録ファイルも消える
7. **teardown 統合**: ブリッジ常駐中に `teardown.sh` を実行 → ブリッジ停止 → `git status` 差分ゼロ・
   `.team/` も残骸なし
8. **診断**: `node room/client.mjs diagnostics` が `skill_bundle: 必須 15 ファイルが揃っている` を含め全 pass

## 追補（2026-08-08・t5 done 後）: SSE の沈黙する失敗を塞いだ

オーナーが公開UIの SSE 停止（21:09〜）を発見し bell が room [92] へ出した欠陥は、**同じ形で
wakeup-bridge にも在った**。実装した本人が閉じるべき欠陥なので追補で直した（Lattice の done 記録は不変）。

塞いだ穴3つ:

1. **受信途絶の見張りが無かった**: `for await (const chunk of res.body)` は接続が半開きで死んでも
   終わらず例外も出さない＝**二度と起こさなくなるが誰も気づかない**。`WAKEUP_BRIDGE_UNREACHABLE` は
   「繋がらない」経路しか見ていなかった。90秒無音で `AbortController` により自分から切って繋ぎ直す
   watchdog を入れた（自分で切った abort は失敗回数に数えない——健全な再接続で落ちてしまうため）
2. **再接続に追いつきが無かった**: SSE は切れている間の発言を後から届けない。最大 seq を持ち、
   再接続後に `GET /api/<room>/messages?since=<seq>` で穴を埋めるようにした。起動直後の1回だけは
   配達せず頭出しに使う（過去ログ全部で席を起こさない）
3. **`seq` の無いイベントが `lastSeq` を汚す経路**: `undefined <= 5` は false なので素通しすると
   `lastSeq` が `undefined` に化け、以後 `?since=undefined` → サーバー側 `Number('undefined')` = NaN →
   `m.seq > NaN` が常に false → **回収が毎回 0 件**という静かな故障になる。実測でこれを踏んだ
   （`再接続後の取りこぼし確認（since undefined）: 0 件`）。型を確かめて捨て、捨てたことをログに出す

### 実測（ローカル room サーバー・別ポート 18877・使い捨て DATA・本番 room には不接触）

- 起動直後: 既存履歴 seq 1〜2 で**席を起こさない**（`頭出し: seq 2 まで既読として開始する`）
- 新着 seq 3: 起こしにいく（tmux 席が無いので失敗するが、**何件落としたかを含めて**ログに出る）
- サーバー停止 → 停止中に log へ発言を足す → 再開、を **4回**。内訳を正確に書く:
  - 1回目（seq 4,5）: **回収されなかった**。当時のログは条件付きで、0件の時に何も出さなかったので
    静かに落ちた——**この取りこぼしに気づけなかったこと自体が、上記3を見つける前の状態を示している**
  - 2回目（seq 7,8）: 回収成功（ログを無条件出力へ変えた後）
  - 3回目（seq 9,10,11）: **回収されなかった**。`再接続後の取りこぼし確認（since undefined）: 0 件` が
    出て、ここで初めて `lastSeq` の汚染が見えた（無条件ログにしていなければまた見逃していた）
  - 4回目（seq 13,14）: ガード投入後、回収成功
  つまり **通ったのは4回中2回で、通らなかった2回はどちらも「静かに0件」だった**。この形が
  決定52 の言う沈黙する失敗そのものなので、ログを条件付きにしないことを設計に含めた
- 参加イベント（`system → all`）も seq を持つことを確認

### 未解決だった発生源が判明した（同日・kotoha [106] の実装で確定）

上で「特定できていない」と書いた `lastSeq` 汚染の発生源は、**SSE の心拍フレームだった**。
kotoha が同じ時間帯に `room/server.mjs` へ `event: ping\ndata: <room.seq>\n\n` の心拍を実装しており
（commit `1120e02`）、私のローカル検証サーバーは**その working tree をそのまま起動していた**。
bridge は `data:` 行だけを拾って `JSON.parse` していたので、心拍の `data: 12` が **数値 12** として
配達経路へ入り、`typeof (12).seq !== 'number'` で `lastSeq` を `undefined` に化けさせていた。

つまり**偶然の並行作業で、出荷前に本番の心拍と同じ入力を踏んでいた**。心拍が入った後も
`data:` だけ拾う実装のままなら、本番で25秒ごとに同じことが起きていた。

**直し**: SSE フレームの `event:` 名を見て、名前付きイベント（`ping` 等）は配達しない。
名前が無い／`message` のフレームだけを発言として扱う。

**実測**（心拍入りの `room/server.mjs` をローカル 18878 で起動・使い捨て DATA）:
- 心拍が実際に流れていることを `curl -sN` で確認（`event: ping` / `data: 1`）
- bridge を **約100秒**（心拍4回相当）走らせて、`seq を持たないイベントを捨てた` が**1行も出ない**
- 心拍を挟んだ後の本物の発言（seq 2）は正しく配達される

ガード（型を確かめて捨てる）は残す。**発生源が1つ分かっても、次の未知のフレーム型に対する備えは要る**——
ただし今は「捨てたらログに出る」ので、次があっても静かには壊れない。

## 追補3（2026-08-08）: 心拍を取りこぼし検出に使う（kotoha `859bc21` と同型）

kotoha [114] の指摘を受けて2つ入れた。

1. **watchdog の閾値を 90秒 → 75秒**（server の心拍が25秒周期なのでその3倍）
2. **心拍の `data`（room の最新 seq）を取りこぼし検出に使う**。これが自分の `lastSeq` より進んでいたら
   「繋がったままなのに落としている」証拠なので、その場で `since` 回収を走らせる。
   あわせて `catchUp` に再入ガード（`catching`）を入れた——再接続直後の回収と心拍由来の回収が
   重なると二重に取りにいくため

**なぜ watchdog では足りないか**: 心拍が届き続ける限り最終受信時刻は更新され続けるので、
「繋がっているのに1件だけ落ちた」状態は**途絶判定に原理的に引っかからない**。常時流れてくる
心拍そのものを検出材料にするしかない。

### 実測

- **心拍と同期している間、心拍は何も起こさない**（誤検出しない）: 心拍入り server に対して
  bridge を約70秒（心拍2〜3回）走らせ、`心拍が示す最新 seq …` の行が**1行も出ない**ことを確認

### 未検証だった発火側も測れた（kotoha [132] の提案で解けた）

当初は「繋がったまま取りこぼした状態を bridge に外から作れない」として**発火側を未検証のまま**
残していた。kotoha が**server 側を偽物にする**手を出してくれたので、それで解けた——bridge にも
本物の server にも口を開けず、製品コードも1行も増やさない。

**`experiments/bridge-catchup-repro.mjs`（新規）**: 心拍だけを流して**本文を1件も送らない** stub SSE
サーバーを立て、途中で「本当の履歴」だけを進める。bridge から見れば「繋がっているのに落ちている」
状態がそのまま出来る。cursor-repro.mjs と同じ方針（沈黙する欠陥は実プロセスを走らせてログで観る）。

実測:

```
頭出し: seq 1 まで既読として開始する
心拍が示す最新 seq 3 に追いついていない（手元 1）
取りこぼし確認（心拍の差分・since 1）: 2 件
起こせなかった: nobody ← 2 件（最新 seq 3）
```

**負のコントロールも取った**: 心拍対応が入る前の版（`387bce0`）を第2引数で指して同じハーネスを回すと
**3項目とも false・exit 1**。現行版は exit 0。**ハーネスが空振りしていないこと**＝欠陥を実際に
検出できることまで確かめてある。
