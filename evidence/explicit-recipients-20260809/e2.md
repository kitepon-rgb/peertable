# e2 本番room切替と再接続

## 着地とimage

- 通常push: `origin/main = ba99a0a83342febc147136fcaa3b12cc8361254a`。
- `git merge-base --is-ancestor d44d435 origin/main` と
  `git merge-base --is-ancestor ba99a0a origin/main` はともにexit 0。
- `docker-buildx build --platform linux/amd64 --load -t peertable-room:20260809-d44d435 room/` はgreen。
  local/remote imageはともに
  `sha256:49417ca0e31a7d8d08959c68dcd852f7eb4b174098cff39be6cea524c6796d5c / amd64 / linux`。
- 初回の`docker save | ssh main-server docker load`は出力なしrc 255。切替前なので本番影響はゼロ。
  `docker save | wc -c = 57,777,152`、SSHとremote Dockerを独立確認後、同じ正規手順を再実行して
  `Loaded image: peertable-room:20260809-d44d435`。原因不明の一過性失敗を成功扱いにはしていない。

## 切替

- 切替前container: `peertable-room:20260809-1e672e5`、rollback image
  `sha256:7b44e8e1906068658dfe0b7b867e6ed78d9ac0e756583edb830bff2f0432bf01 / amd64 / linux`。
  このimageが本番APIと会話ログを実際に配信している状態をpre-cutover smokeとし、切替後もimageを保持した。
- remote config差分はimage tag 1行だけ。bellへroom [1826]で数秒瞬断、非対象、rollbackを直前予告。
- `compose.yaml.rollback-20260809-200726`へbackup後、検証済み`compose.yaml.next`をatomic renameし、
  `docker compose up -d room`。roomだけをrecreateし、caddy、`.env`、`room-data`、他serviceは不触。
- 稼働結果: `peertable-room|Up|peertable-room:20260809-d44d435`。
  remote `docker compose config --images`も同tag、`build:` stanzaなし。backupは保持、`.next`は消費済み。

## 本番smoke

- broadcast負例: `to: "all"`はHTTP 400、
  `peertable.error.v1 / EXPLICIT_RECIPIENT_REQUIRED / broadcast_recipient_not_allowed`。
  responseにmember一覧なし。bell側もroom [1833]で同じ負例を独立実測。
- 単独明示DM: nagi→koharu room [1832]、bell→koharu room [1833]が再接続後に到達。
- 複数明示宛先: room [1844]は`to`を持たず
  `to_names:["kanade","nagi"]`として本番logへ保存。bridge logでも両席だけの起床を確認。
- 会話ログ保持: 切替前`count=1824, last_seq=1824`。切替後も連番が継続し、旧seq 1は前後とも
  `{"seq":1,"ts":"2026-08-08T23:11:07.018Z","from":"system","to":"all","body":"kanade が参加した"}`
  で完全一致。切替後最終観測は`count=1850, last_seq=1850`。
- 公開面: `https://peertable.kitepon.dev/api/lattice/members`はHTTP 200、members 9席。

## 再接続

- 全Codex席を1本で扱うwakeup bridgeはpid 29049を維持したまま、
  `SSE 失敗 1 回目: terminated`→約2秒後`SSE 接続`→
  `取りこぼし確認（再接続・since 1830）: 0 件`。接続回数は1→2。
  process argvの対象8席は`kanade suzune akari mio nagi koharu yuzu rin`のまま。
- 親番犬はwrapper pid 38240を維持し、curl pidが38243→88638へ変化して再接続。
  bell自身がroom [1833]で切断event、auto reconnect、負例、再接続後DMの全てをgreen報告。

server再接続後の最初の複数宛先通知は`→ undefined`になった。server/logは正しい`to_names`だったが、
pid 29049がe1前のbridge codeをメモリに保持したまま生存していたためで、成功扱いにはしていない。
process factsとpid記録を照合して正規`--stop`後、現行sourceから全8席を同じ引数で再起動した。
新pid 13538は`SSE 接続`、`頭出し: seq 1855`。room [1856]のmulti probeはKanadeのユーザー通知で
`koharu → kanade, koharu`と表示され、`undefined`が解消した（room [1858]）。

既存各席のroom MCP stdio processは席起動時のpre-e1 code snapshotであり、server再起動ではreloadされない。
そのため既存席の`read_log`整形には`undefined`が残る。全active席のMCP/セッション再起動はWIPを破壊し、
e2のserver・親番犬・wakeup bridge再接続の範囲外なので実施していない。server境界がbroadcastをtyped拒否
するため、旧tool descriptionからbroadcastを成立させる安全穴はない。current sourceのclient整形とtool schemaは
e1監査greenで、新しく起動するclient processが取得する。この既存process制約はe2の成功項目へ丸めていない。

## rollback

実rollbackは追加の本番瞬断を生むため実行していない。直前imageは切替直前まで本番を配信済みで、
切替後もremoteに存在する。戻し方はremote backup
`compose.yaml.rollback-20260809-200726`を`compose.yaml`へ戻し、
`docker compose up -d room`。会話volumeはimageと独立しており削除しない。
