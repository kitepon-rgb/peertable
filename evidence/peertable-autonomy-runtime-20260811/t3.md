# t3 provider-neutral な親 role と Codex 親の入口を作る

## 何を作ったか

1. `skill/templates/parent.md`（新規）: provider-neutral な親 role 文書。既存 `skill/SKILL.md`
   の「親の operating notes」を土台に、§2.4（親が行わないこと: 技術監査・通常のLattice
   task起票/start/note/done・配車・peer audit不足補充）を明記し、Claude/Codex で手順が異なる
   箇所（新着検知: Claude=Monitor番犬 / Codex=wakeup-bridge）を分岐して書いた。
2. `skill/scripts/setup.sh`: `.team/roles/parent.md` を `parent.md` テンプレートから生成する行を
   追加（charter.md のコピー直後）。mode（lattice/standalone）を問わず生成する。
3. `skill/scripts/parent-join.sh`:
   - 第5引数 `vendor`（`claude`|`codex`、既定は model 指定時 `claude`）を追加し、Codex 親を
     member 登録できるようにした。
   - owner裁定[46]④（親の通常shellでLattice mutationを打つとACTOR_UNRESOLVEDで無変更停止する。
     子processのexportは親shellへ伝播しないため）への対応として、`setup-state.json` の
     `mode === 'lattice'` の時だけ `.team/parent-env.sh` を生成する。中身は
     `LATTICE_TODO_ACTOR_HOST`/`SESSION`/`AGENT` を親名で export する3行。生成後、
     `source .team/parent-env.sh を実行すること` を出力する。
   - **（tsubaki監査[95]対応）** 親が tmux 内で動いていれば `tmux display-message` で自分の
     `socket_path`/`pane_id` を読み、member 登録の `observe` 欄へ含める（席と同じ観測記述子）。
     `vendor=codex` かつ observe が取れた時は `ensure-bridge.sh <proj> wakeup <name>` を自動起動
     する。tmux 外（observe が取れない＝外部注入面が無い host）の場合は、自動配線を諦めて
     「room の新着は read_unread を自分で定期的に呼ぶこと」という制約を明示する
     （campaign文書t3の代替パスに従う）。
4. `experiments/parent-role-repro.mjs`（新規）・`experiments/parent-wakeup-e2e-repro.mjs`
   （新規）: 上記を実測するハーネス。

## どう確認したか

```
$ node experiments/parent-role-repro.mjs
  pass  setup.sh（単独）が成功する
  pass  .team/roles/parent.md が生成される
  pass  parent.md が親の行わないことを明記
  pass  parent.md が vendor 分岐（Claude/Codex の新着検知）を明記
  pass  parent-join.sh（lattice）が成功する
  pass  mode=lattice で .team/parent-env.sh が生成される
  pass  parent-env.sh が LATTICE_TODO_ACTOR_* を親名でexportする
  pass  vendor=codex が member 登録へ反映される
  pass  parent-join.sh（standalone）が成功する
  pass  mode=standalone では .team/parent-env.sh を作らない
  pass  親が tmux 内なら observe（tmux_socket/tmux_target）を自己申告する
  pass  observe が在れば wakeup-bridge 起動を試みる（ensure-bridge.sh 呼び出しの痕跡）
parent role repro: green
```

**（tsubaki監査[95]対応の実測）** 実 room server（`room/server.mjs` を fixture として子プロセス
起動、SSE 対応）＋実 tmux pane で、observe 記述子を持つ親宛メッセージが `wakeup-bridge.mjs` 経由で
実際に tmux pane へ `send-keys` されることを確認した:

```
$ node experiments/parent-wakeup-e2e-repro.mjs
  pass  fixture room server が起動する
  pass  wakeup-bridge が起動しready_atを立てる
  pass  親宛メッセージが実際にpaneへsend-keysで届く（wakeup-bridge経由）
parent wakeup e2e repro: green
```

これで「parent-join.sh が observe を自己申告する→wakeup-bridge がそれを解決する→実際に通知が
届く」という一連の入口配線が実測で確認できた（tsubaki[95]が指摘した「wakeup-bridge.mjsの起動・
pid記録・親名への紐付けをしていない」という配線欠落そのものを埋めた実測）。

`bash -n` で3つのシェルスクリプト（setup.sh・parent-join.sh・harness が呼ぶ全て）の構文を確認。
`teardown.sh` は `.team` ディレクトリ全体を `rm -rf` する既存実装なので、新規ファイル
（`.team/roles/parent.md`・`.team/parent-env.sh`）も追加対応なしで撤去される
（`teardown.sh:302` の既存コードで確認、コード読解）。

owner裁定[46]④の負例（`lattice todo reopen` を素の shell で打つと `ACTOR_UNRESOLVED` /
`missing_environment=[LATTICE_TODO_ACTOR_HOST,LATTICE_TODO_ACTOR_SESSION,LATTICE_TODO_ACTOR_AGENT]`
で無変更停止する）は bell の一次情報（room [54]）であり、本 task の受入は `todo note`（t3,
2026-08-11T07:55Z）へ先に記録済み。

## 未実測・残課題（正直に記載）

- **配線の到達自体は実測済み**（上記 `parent-wakeup-e2e-repro.mjs`）。未実測なのは、その先の
  **実 Codex CLI プロセスが実際にそのターン内で通知を読み `read_unread` を呼ぶ steering の挙動**。
  これは実際に Codex CLI（API 呼び出しを伴う）を親として動かす必要があり、本 task では実施
  していない——ただし Codex がターン実行中でも素送信を受け付けること自体は SKILL.md に
  既存の実測記録（2026-08-08・Codex CLI v0.146.0、席起動時の実測）があり、親固有の未知数ではない。
- **Desktop での wake 成立可否**: 本 host は CLI 環境のみで、Claude/Codex Desktop アプリでの
  外部注入面の検証はこの host では行えない（制約として明示。継続監視の正規手順は
  parent.md の「Codex: ...この経路は Desktop/CLI どちらでも同一の wakeup-bridge を使うため、
  Desktop での注入成立可否は個別に確認すること」に明記済み）。
- vendor=codex の member 登録は fixture server（`room/server.mjs` 実プロセス）での実測により
  スキーマ受理を確認済み（上記 e2e repro）。
- **完了検知・黙った照合・差し戻しが成立する正規入口**（親が peer audit 済み done を検知し、
  green なら無言・欠陥なら reopen する一連）は、親（このセッション自身）が既に本 campaign で
  実践しているプロセスそのもの（bell の各種 `[差し戻し]`・`[実測欠陥]` 発言）であり、Claude 親
  としては実測済みと言える。Codex 親でこの一連を実際に動かす検証は t4 の実円卓統合が担う
  （campaign文書t4のdesign_memo「Codex 親が工程内監査と工程管理を奪わないことを一連で測る」）。

## 受入条件

- provider-neutral な親 role が setup 時に生成される — 確認済み。
- parent join が Claude / Codex どちらにも同じ役割境界（§2.4）を提示する — 確認済み
  （parent.md 本文、fixture 検証）。
- 親の通常 Lattice 操作が read-only 観測と defect 時の reopen に限定される — parent.md に
  「親が行わないこと」として明記（コードでの強制はしていない。役割文書レベルの契約）。
- owner裁定[46]④の受入（3値が正規の親identityで供給され各commandで手入力不要、未配線なら
  実行前診断で次の正規入口が分かる）— `parent-env.sh` により手入力不要を達成。「未配線ならの
  診断」は Lattice CLI 自体が返す `ACTOR_UNRESOLVED` エラーメッセージ（`next_action`込み）が
  実質的にその役割を果たすため、parent-join.sh 側に追加の診断は実装していない
  （過剰設計を避ける判断）。
