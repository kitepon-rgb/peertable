# t3 provider-neutral な親 role と Codex 親の入口を作る

## 何を作ったか

1. `skill/templates/parent.md`（新規）: provider-neutral な親 role 文書。既存 `skill/SKILL.md`
   の「親の operating notes」を土台に、§2.4（親が行わないこと: 技術監査・通常のLattice
   task起票/start/note/done・配車・peer audit不足補充）を明記し、Claude/Codex で手順が異なる
   箇所（新着検知: Claude=Monitor番犬 / Codex=wakeup-bridge）を分岐して書いた。
2. `skill/scripts/setup.sh`: `.team/roles/parent.md` を `parent.md` テンプレートから生成する行を
   追加（charter.md のコピー直後）。mode（lattice/standalone）を問わず生成する。
3. `skill/scripts/parent-join.sh`:
   - 第5引数 `vendor`（`claude`|`codex`、既定は model 指定時 `claude`）を追加し、Codex 親を
     member 登録できるようにした。
   - owner裁定[46]④（親の通常shellでLattice mutationを打つとACTOR_UNRESOLVEDで無変更停止する。
     子processのexportは親shellへ伝播しないため）への対応として、`setup-state.json` の
     `mode === 'lattice'` の時だけ `.team/parent-env.sh` を生成する。中身は
     `LATTICE_TODO_ACTOR_HOST`/`SESSION`/`AGENT` を親名で export する3行。生成後、
     `source .team/parent-env.sh を実行すること` を出力する。
   - **（tsubaki監査[95]対応）** 親が tmux 内で動いていれば `tmux display-message` で自分の
     `socket_path`/`pane_id` を読み、member 登録の `observe` 欄へ含める（席と同じ観測記述子）。
     `vendor=codex` かつ observe が取れた時は `ensure-bridge.sh <proj> wakeup <name>` を自動起動
     する。tmux 外（observe が取れない＝外部注入面が無い host）の場合は、自動配線を諦めて
     「room の新着は read_unread を自分で定期的に呼ぶこと」という制約を明示する
     （campaign文書t3の代替パスに従う）。
4. `experiments/parent-role-repro.mjs`（新規）・`experiments/parent-wakeup-e2e-repro.mjs`
   （新規）: 上記を実測するハーネス。

## bell[121] 親の再着卓導線への追加対応

`parent.md` の「親の再着卓」は従来、roomログを読む順序だけを示し、新しいshellへ
`PEERTABLE_POST_TOKEN`・room URL/nameを戻す具体的な入口を持たなかった。bellは抽象名 `$TOKEN`
から誤った環境変数を2回試した後、`~/.config/peertable.env` の実物照合で初めて正しい変数名へ
到達した（room[121]）。これを個体の操作ミスではなく再着卓導線の欠陥として修正した。

- `PEERTABLE_PROJECT` と親名だけを指定し、正規config `~/.config/peertable.env` をsourceする実行可能な
  shellブロックを `parent.md` へ追加した。tokenは画面へ表示・転記しない。
- `setup-state.json` から URL と room 名を復元し、room pathをpercent-encodeする。日本語roomも同じ
  入口で扱う。
- `peertable_parent_read <since>` と `peertable_parent_post <to> <message>` を定義し、抽象名
  `$TOKEN` や手組みJSONを使わないcopy-safeなread/post入口を一続きで示した。
- `experiments/parent-role-repro.mjs` はrole内の実ブロックを抽出し、`PEERTABLE_POST_TOKEN` をunsetした
  新shellで実行する。fixture configのsource、Unicode roomのread、正規tokenと安全なJSONによるpost、
  stdout/stderrへ秘密値が出ないことを実room fixtureで確認する。

実測結果:

```
  pass  parent.md に実行可能な再着卓 shell ブロックがある
  pass  token 未設定の新 shell から再着卓 read/post が成功する
  pass  再着卓の標準出力・標準エラーへ秘密値を出さない
  pass  Unicode room path を percent-encode して読む
  pass  正規 token と安全なJSONで親の投稿が届く
parent role repro: green
```

負のコントロールとして、使い捨てrepoコピーの `parent.md` から正規configのsource行だけを削除して
同じハーネスを実行した。`PEERTABLE_POST_TOKEN ... が必要` でread/post前に停止し、3項目がFAIL、
exit 1（`mutation_rc=1`）になった。canonical fileは変更していない。

## tsubaki監査[108][109][110]への追加対応

tsubakiが実 Codex CLI 0.147.0 で `codex mcp list` を確認したところ room connector が登録されて
いなかった（room[110]）。これは欠陥ではなく設計どおりと判断した: `launch-seat.sh` の
`-c mcp_servers.room...` はコマンド起動時のワンショットオーバーライドで、グローバル設定を見る
`codex mcp list` には反映されない。そして親は「専用親セッションは作らない」設計（決定40）なので、
親の Codex CLI セッションは最初から `-c mcp_servers.room...` を経ておらず、room MCP を持たない
のが正しい——これは Claude 親の既存原則「親は MCP を後付けできないため room へは HTTP API 直で
入る」が Codex 親にも同じ理由でそのまま当てはまる、という話である。

`parent.md` の Codex 節に、wakeup-bridge が送る通知文言（`read_unread で読むこと`）は席向けの
定型句であり、親はこれを文字どおり `read_unread`（MCP ツール）としてではなく
`curl .../messages?since=...` として読み替えることを明記した（commit 次項）。tsubaki[109]が
実測した「parent-join.sh 自体を実行する fixture」で join→自動bridge→通知到達が green だったこと
と合わせ、**入口の配線自体（wakeup-bridge が親を起こせること）は完全に実測済み**と整理できる。

room MCP を持たない既存親セッションをそのまま使い、親 role の HTTP helper と実
`wakeup-bridge.mjs` を組み合わせれば、このhost上の現 Codex CLI を作り直さずに残りを測れると判明した。
次節の実測で「t3では実測不能」という上記の仮説を棄却した。

## 実 Codex CLI 親ライフサイクル smoke

Codex CLI 0.147.0 で動いている現 `nagi` セッションを fixture 親として使い、別エージェントは
起動しなかった。使い捨ての実 room server、実 `wakeup-bridge.mjs`、一意な project id を持つ実
Lattice store（plan `t3-parent-fixture` / task `t1`）を用意した。既存親の tmux observe を memberへ
登録し、親 role に埋め込んだ再着卓 shell ブロックをファイルから抽出して、そのまま read/post に使った。

green 経路:

1. `t1` を start→evidence commit→正規 `done.sh` で done にした。
2. `fixture-worker → nagi` の `[done]` を room へ投稿すると、実 bridge が現 Codex CLI の会話へ
   `room に新着あり（fixture-worker → nagi）。read_unread で読むこと。` を注入し、新しい親 turn が
   実際に開始した。
3. 通知の定型句を親 role どおり HTTP read に読み替え、room seq 2 を取得した。
4. `contract.txt=green contract`、evidenceあり、Lattice active/readyなしを照合した。
5. room 全2件中 `from=nagi` は0件で、green 時の沈黙を確認した。

欠陥経路:

1. fixture の `contract.txt` だけを `broken contract` へ変え、同じ宛先へ再通知した。実 bridge が
   再び現 Codex CLI の親 turn を開始した。
2. HTTP read で room seq 3 を取得し、evidenceは存在するが contract が不一致、かつ task は done の
   まま、と確認した。
3. 正規の親 actor 3値を付けて `lattice todo reopen --plan t3-parent-fixture --task t1` を実行し、
   mutation result `status=in-progress` を得た。続く status で `active_set=[t1]` を確認した。
4. 親 helper の `peertable_parent_post` で `fixture-worker` 宛てに
   `[差し戻し] contract.txtがbroken contractで受入不成立。...をreopenしました。` だけを返した。
   room の `from=nagi` はこの1件だけで、宛先・欠陥理由・reopen通知を機械照合した。

これにより、Codex 親について wakeup による実 turn steering、MCPなしの正規 read/post、done の
green照合時の沈黙、欠陥時だけの reopen と宛先限定差し戻しまでを一連で実測した。

  外部注入面の検証はこの host では行えない（制約として明示。継続監視の正規手順は
  parent.md の「Codex: ...この経路は Desktop/CLI どちらでも同一の wakeup-bridge を使うため、
  Desktop での注入成立可否は個別に確認すること」に明記済み）。
- vendor=codex の member 登録は fixture server（`room/server.mjs` 実プロセス）での実測により
  スキーマ受理を確認済み（上記 e2e repro）。
- **CLI の完了検知・黙った照合・差し戻し**は上記 fixture で実測済み。t4 はこれを再び成立させる
  入口検証ではなく、実円卓全体で Codex 親が工程内監査と工程管理を奪わないことの統合検証を担う。

## 受入条件

- provider-neutral な親 role が setup 時に生成される — 確認済み。
- parent join が Claude / Codex どちらにも同じ役割境界（§2.4）を提示する — 確認済み
  （parent.md 本文、fixture 検証）。
- 親の通常 Lattice 操作が read-only 観測と defect 時の reopen に限定される — parent.md に
  「親が行わないこと」として明記（コードでの強制はしていない。役割文書レベルの契約）。
- owner裁定[46]④の受入（3値が正規の親identityで供給され各commandで手入力不要、未配線なら
  実行前診断で次の正規入口が分かる）— `parent-env.sh` により手入力不要を達成。「未配線ならの
  診断」は Lattice CLI 自体が返す `ACTOR_UNRESOLVED` エラーメッセージ（`next_action`込み）が
  実質的にその役割を果たすため、parent-join.sh 側に追加の診断は実装していない
  （過剰設計を避ける判断）。
- bell[121]の再着卓受入（token未設定の新shellから、秘密値を表示せず正規configをsourceし、
  copy-safeなroom read/postまで到達する）— role内の実行ブロックをそのままfixture shellで実行して
  確認済み。config sourceを消した負のコントロールで測定器も検証済み。
- 実 Codex CLI 親の受入（wakeup→read→done照合→green時沈黙／欠陥時reopen＋差し戻し）—
  Codex CLI 0.147.0 の現セッションと実 room/Lattice fixture で両分岐を確認済み。
