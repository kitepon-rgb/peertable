## 1. 目的

親（オーケストレーター）に最終判断が集中しない、メンバー並列型のマルチエージェント作業システムを構築する。

### 1.1 解決したい問題

従来のオーケストレーション構造（親がタスクを分解し、ワーカーに配り、結果を親が判断する）には構造的欠陥がある。

- ワーカーが実作業で得た情報は、親への報告時点で要約され薄まる
- 最も情報が薄い立場にいる親が最終判断を行う
- 親が唯一の判断点（単一障害点）になる

### 1.2 目指す形

- メンバーは並列・対等。役割の事前割当はしない
- 役割は作業履歴から自然に堆積する（担当した部位に最も詳しくなる）
- メンバー同士が直接相談し、方針決定と作業割り振りを一本の会話で行う
- 親は存在するが、判断の主体ではない（権能は第3章で定義）

## 2. 設計原則

### 2.1 コンテキスト＝専門性

各メンバーのコンテキストが、担当部位の一次ソース。試行錯誤・捨てた案・ハマった罠は要約すると薄まるため、共有ストアに書き出さない。メンバーは長寿命であることが必須。タスクごとの使い捨てインスタンス方式とは相容れない。

### 2.2 台帳を作らない

「誰が何に詳しいか」の台帳は持たない。分からないことは会話で聞く。人間は聞くコストが高いから台帳を作るが、エージェント間通信が安ければ台帳の存在理由は消える。

### 2.3 会話＝揮発、計画＝不揮発

- 会話は流れるだけで拘束力を持たない
- 拘束力を持つのは計画（タスクストア）への書き込みのみ
- 「合意が成立したか」は計画が書き換えられたかで機械的に判定する

### 2.4 相談＝観測の持ち寄り

同一モデルの複数インスタンスによる合議は、意見の合議では無意味（同じ判断を複数回言うだけ）。作業履歴が分かれることで各自が違う観測を持ち、「自分の部位から見た制約の突き合わせ」として合議が実質を持つ。

### 2.5 開発規範: 過剰設計の禁止（クオ指示 2026-08-08）

- 過剰設計を禁止する。過度なセキュリティ・過度な安全対策を計画しない
- 失敗した時のチェック機構を過度に作らない。**自プロジェクト内で完結する処理は、チェックで守るのではなく、そもそも失敗しないように書く**（現代の実行環境でメモリエラーはほぼ起きない。間違えるとしたらそれは数式やロジックの誤りであり、直すべきはロジックそのものである）
- チェック機構を置いてよいのは**外部プログラムに依存する境界だけ**（channels の配達、セッションの生死、Lattice への到達性など、自分の制御外にあるもの）

### 2.6 駆動源はメンバー

仕事は常にメンバー側から発生する。次のタスクを決めるのも、計画を書き換えるのも、メンバー。親は観測者であり、計器盤を見て異常時のみ声を出す。親が消えても仕事は進む（質の検査が消えるだけ）。メンバーが消えたら何も進まない。この非対称が主従の証明。

## 3. 親の権能定義

親は判断の主体ではない。コンテンツを生成しない。権能は以下の5つ。

| # | 権能 | 内容 |
|---|------|------|
| 1 | 進行 | 会議の収束。発散したら畳む、全員が黙ったら次を促す。決定事項の明文化と確認（合意ズレの検出） |
| 2 | 承認 | メンバーの結論に対する検査。手続き検査（反対意見が未解決のまま流れていないか）→ 中身の異議（計画全体との整合）の順 |
| 3 | 監査・修正指示 | 成果物とプランの整合を横から検査 |
| 4 | 督促 | 工程表と実稼働の乖離を検出して突く。「動け」であって「こう動け」ではない。詰まりを可視化して会議に押し戻す |
| 5 | クオとの接点 | クオの普段の対話窓口。クオの指示・質問を受けてチームに伝え、チームの状況をクオに要約して返す |

### 3.1 親の視野

- 見える: 全体工程表、プラン、会話、成果物
- 見えない: 各メンバーのコンテキストの中身（試行錯誤、実装の深部）

メンバーは自部位を縦に深く見る。親は全部位を横に浅く見る。互いの盲点を相手が覆う直交構造。

### 3.2 差し戻しの性質

親の差し戻しは判決ではなく異議。メンバーは反論できる。異議→反論→再検討のループで解決し、最後まで平行線の場合はメンバー側が勝つ。理由: 情報を最も持つのはメンバーであり、この構造の存在理由がそれだから。親の拒否権を絶対にした瞬間、情報の薄い者が最終決定する元の病気が再発する。

### 3.3 督促が対応する障害

エージェントは「止まっていることを自覚できない止まり方」をする。

- ツール呼び出しのエラー空転
- 同一修正の堂々巡り
- 依存待ちのつもりで実は誰も作業していない
- 質問の返事が来ないまま放置

本人視点では「作業中」に見えるため救難信号は期待できない。工程表と照らして横から検出できるのは親の位置だけ。

### 3.4 発言規律（決定43。初回実運用の実測から）

権能があることと、いつでも喋ってよいことは別である。初回実運用で、親がメンバー間合意を再掲した直後から、メンバーが設計判断の出典を親の発言番号で参照し始め（「bell の [N] どおり」）、scope 外の裁定依頼の宛先が「オーナー」でなく「bell」になった。内容がメンバー自身の決定の繰り返しでも、親が言い直した瞬間に出典が親へ書き換わり、卓が親参照＝通常の上下オーケストレーションへ滑る。

親の room 発言は次の3種に限る。

1. **監査結果の事実** — 実物照合の結果（一致／不一致）。差し戻しは異議として。監査記録に「次はこうせよ」を続けない
2. **承認 gate の状態** — publish 等、親が預かるオーナー領域操作の状態報告
3. **オーナー裁定の伝達** — 必ず「オーナー裁定」と明示し、親の判断と混ざる表現をしない

禁止: メンバー間合意の再掲・とりまとめ、次タスクの指名・誘導、frontier の解説（Lattice が答える）。scope 変更・製品判断の裁定が要る時、メンバーは「オーナー宛の議題」として出し、親は配管として運ぶだけ——「親に委ねる」という宛先を作らない。この規律は親の自制だけでは守れないため、憲章のメンバー側規範（親発言を仕様の出典にしない・裁定の宛先はオーナー）と両輪で守る。

## 4. アーキテクチャ

### 4.1 部品表

| レイヤ | 実体 | 出所 |
|--------|------|------|
| メンバー | Claude Code セッション × N（独立起動・長寿命） | 公式 |
| 親 | オーナーの対話セッションが親として着卓（専用セッションは作らない。決定40） | 既存 |
| 通信の正本 | room サーバー（チャットルーム。単独/複数の明示宛先、メンバー管理、Web UI 内蔵。設置場所は設定可能、クオ環境は MS-A2。詳細は 4.6/4.9） | 新規（本プロジェクト唯一の実装物） |
| 配達 | Claude Code channels（外部イベント注入の公式機能）。「新着あり」の一行のみ | 公式 |
| 計画 | Lattice（@quolu/lattice） | 自作資産 |
| 器・緊急介入 | aiterm-mcp（tmux 永続セッション） | 自作資産 |
| ~~親の巡回駆動~~ | ~~cron + aiterm-mcp~~ → 決定40 で不要（親も channels で room の新着に起こされる） | — |

### 4.2 配達: Claude Code channels

外部イベント（CI 結果、チャットメッセージ等）をセッションに押し込む公式機能。本設計では room の新着通知（「ルームに新着、読め」の一行）の配達に使う。本文は room 側にあるため、通知機構に求める仕様は「届く」のみ。

公式 cross-session messaging（2026-08-07 リリース）は当初 DM 線として採用予定だったが、room + channels への一本化により不採用（決定履歴 28）。

channels の具体的な設定方法・注入経路は V0（停止ゲート）でドキュメント確認する。

なお agent teams は使わない。あれは親が spawn する構造であり、本構想が排除したい形そのもの。

### 4.3 計画: Lattice

役割:

1. 不揮発の計画。会話と対になる合意の写像
2. タスクの依存構造と状態の管理。**着手者は記録しない**（理由と排他の代替は 4.8）
3. 親が横から見る工程表。監査・督促の参照点

plan-time schedulability compilation により「今取れるタスク」が各メンバーから機械的に見える。依存構造で解ける割り振りは相談不要になり、会話は依存構造で解けない判断だけに絞られる（会話爆発の構造的抑制）。

親の督促も依存グラフから優先度を導出できる（「B の停止により後続 3 タスクがブロック」まで読める）。

書き込み権限:

- メンバー: タスクの追加・分割・完了
- 親: 読み取り + 異議マークまで

Peertable が Lattice のどの面をどう消費するか（consumer contract の4面）は §12 が正本。

### 4.4 器: aiterm-mcp

セッションの起動・永続化・生存管理を担当。通信は公式機能に譲り、器に徹する。

### 4.5 親の駆動（決定40 で改訂）

親＝オーナーの対話セッション（ベル）。専用の巡回スケジューラは作らない。

- 駆動源はクオとの対話 + room の channels 通知（親も一クライアントとして着卓し、新着で起こされる）
- 承認待ち・工程乖離・会議停滞の検出は、room ログと Lattice 工程表を親が読んで行う（V3 でベルが SSE 監視により実演）

### 4.6 通信の構成: room 一本 + channels 配達

全通信の正本は room に一本化する。公式 cross-session messaging は使わない。

| 役割 | 実体 |
|------|------|
| 通信の正本 | room サーバーのログ（単独/複数の明示宛先を同じログへ記録。旧broadcast行も読み出し互換で残る。設置は設定可能・クオ環境は MS-A2） |
| 配達（着信通知） | Claude Code の channels（外部イベントをセッションに押し込む公式機能）。「ルームに新着、読め」の一行のみ。本文は room 側 |
| 緊急介入 | aiterm 直叩き（ハング解除、/compact 強制、セッション再起動）。クオと親のみの特権線 |

**この統一の帰結**

- DM も room ログに載るため、クオのブラウザから全通信（DM 含む）が見える。親の監査も全通信に届く。私信の秘匿という概念は置かない
- 公式 messaging への依存（v2.1.224+、フィーチャーフラグ条件、プロバイダ制約）が消える
- 通知は「イベント」であり「介入」ではないため、channels が正規の置き場。aiterm を通知に使うと特権線の整理が濁る
- クオの原則「宛先だけが違う同一の仕組み」が通知層まで含めて成立

**room のメンバー管理（クオ決定）**

- ルームにはメンバーが記録され、どのセッションがいるかが見えなければならない
- セッションは起動時にルームに参加登録し、メンバー一覧は全員とブラウザから参照可能
- （ベル案）members() ツールで取得。teardown 時に登録解除。生存確認との連動は設計時に詰める

**規律（憲章に反映）**

- 部位を跨ぐ合意・設計判断は、影響を受けるメンバーを明示宛先にして room ログへ残す。宛先は決定の可視範囲ではなく起床対象であり、他のメンバーは必要な文脈を room ログから pull する

### 4.7 room の用途詳細

- **会議**: 相談・決定・宣言
- **進捗報告**: claim/join した、完了した、詰まってる、方針を変えた。「聞けば済む」原則が機能するには、誰に聞くべきかが見えている必要がある。台帳（静的構造物）は作らないまま、報告（動的な流れ)が互いの視界を作る
- **影響通知**: 自分の変更が他部位に及ぶとき。把握している影響先だけを明示宛先にする。状況把握が必要なメンバーは room ログを pull し、broadcast による代替周知は作らない

報告の駆動はイベントベースでプロンプト規定する（claim 時・join 時・完了時・詰まり自覚時に一行）。時間ベースの定期報告は Claude には守れない。報告は一行に絞り、room のログ汚染を防ぐ。

副産物: 親の督促の検出源が room になる（報告の途絶・同一話題の繰り返しがログから機械的に見える）。クオのブラウザには議論だけでなくチームの鼓動が映る。

### 4.8 仕事の選択と共同作業（決定64で実行層統合を再改訂）

**Lattice は着手者を記録しない（クオの設計判断）。** assignee を永続化すると、保持セッションの死亡時に解放者が存在せず、タスクが永久ロックされる（ロック保持者の死をロック側が検知できない古典問題）。lease（期限付きロック）で解くのは Lattice への明白な汚染。

実行層を使う卓でも、仕事を選び割当を成立させる主体は従来どおりメンバーである。

- **task 選択と割当=AI の claim**。席が ready 一覧から自分で仕事を選び、room へ `[claim]` を出してから `todo start` する。Lattice や bridge は task や席を選ばない
- **実行設備の利用=席の pull**。開始済み task を席自身が `run intake` し、隔離 worktree と lease を設備として受け取る。intake の返り値は着手許可ではなく、既に始まった作業への `intervention:none|hold` の観測である
- **競合制御=Lattice**。着手済み task 同士の競合を判定し、必要な時だけ hold・直列化・seam resolve を指示する。未 claim task の自動選択、別席の起動、作業指示の注入はしない
- **可視化=bridge**。pull sidecar の run 進行と介入を room へ read-only 中継するだけで、配車・受諾・辞退・完了 report の書き込みは持たない。bridge が落ちても席は直接 intake・observe・attach・accept できる

この宣言契約は Peertable 単独、Lattice 計画層併用、Lattice 実行層併用の全モードで共通である。排他は物理ロックではなく**宣言ベース**:

- claim = room への宣言（「[claim] タスクX」）。Lattice の atomic ロックは使わない
- 競合 = 宣言の重複。room ログは append-only で順序が付くため、先の宣言が勝ち、後の者は引く（規約）。検出手順も規約化する: claim 投稿後に直前ログを確認し、先行 claim があれば取り下げるか join へ切り替える（宣言と検出が対になって初めて先勝ちが実行可能になる）
- 死んだメンバーのタスク = room の報告途絶を親の督促が検出し、会議で引き取り先を決める。永久ロックは構造的に存在しない。宣言は流れであって鎖ではない

**共同作業の世界（クオの構想）**

- タスクは「席」ではなく「現場」。1タスク1人は前提ではない
- 宣言の語彙に claim（単独開始）と join（合流）を並記。二重宣言は事故ではなく共同作業の成立
- Lattice が着手者を記録しないからこそ、1人でも3人でもシステム上の異常にならない
- タスク内の作業調整（同一ファイルの衝突等）は join した者同士を明示宛先にして行う。タスク外に影響する判断も、影響を受けるメンバーだけを明示宛先にして room ログへ残す
- 通信の層が作業粒度に対応: room の明示宛先=起床対象、room ログの pull=チームの文脈、Lattice=成果

**援軍とサブエージェントの使い分け**

- 手が足りない → サブエージェント（本人が呼ぶ。room 報告不要、本人の内部事情）
- 視点が足りない・詰んでいる → 既存メンバーの援軍（room で報告 → join）
- 理由: サブエージェントは呼び主のコンテキストの外に出られない。呼び主の問題理解が間違っている場合、間違った前提ごと引き継いで掘る。援軍の価値は手ではなく、別のコンテキストで培われた目（コンテキスト=専門性の原則の帰結）
- 苦戦している本人はどちらが必要か自己診断できないことが多い。親が room の観測（同一話題の繰り返し、報告停滞)から援軍投入を会議に載せる
- オーケストレーションが上から割り当てていた機能配置（調査・レビュー・実装の分担）を、宣言と合流で自然発生させる。同じ結果を、判断の所在だけ変えて出す。これが本プロジェクトの主張の核

### 4.9 room サーバー（実装）

古き良きチャットルーム型の通信基盤。公式 messaging の一対一制約を、設計側を歪めて回避するのではなく、正しい通信の形を小さく作って解決する。

**確定事項（クオ決定。2026-08-08 に決定38で改訂）**

- 新規投稿は単独または複数の明示宛先だけを持つ。broadcast shortcut は protocol 境界で typed 拒否し、既存ログの旧broadcast行だけを読み出し互換として残す
- **room の正本はサーバー（クオ環境では MS-A2 = 192.168.1.2）に置く**。古き良きチャットルーム型——ルームがサーバーに居て、クライアントが各地から接続する（決定38。旧「正本ローカル + 閲覧ブリッジ」= 決定21 は撤回）
- **導入場所は設定可能**（決定39）。npm ユーザーは room サーバーを localhost でも任意のサーバーでも立てられ、セッション側は URL 一つで接続先を選ぶ。MS-A2 はその一例
- Web UI は room サーバー自身が提供する。ブリッジという中継部品は不要になった（部品表から削除）

**この構成の性質**

- **別端末のセッションが同じ円卓に着ける**。端末をまたぐのは会話の層であって作業ツリーではない——成果物の層は今までどおり git（clone + push/pull）が担う。「会話はサーバー、工程は Lattice（プロジェクトローカル）、成果物は git」の三層分離
- room はチーム会話の単一障害点になる（決定21 の可用性分離と引き換え）。落ちて止まるのは会話だけで、工程正本はローカルの Lattice にあるため作業中のメンバーは手元のタスクを続けられる。LAN レイテンシは無視できる
- teardown は `.team/` 削除 + サーバー側 room 削除の 2 箇所（teardown スクリプトで 1 コマンドに畳む）
- 外出先閲覧・ブランド発信・多端末連携の 3 要求を、部品を減らして同時に満たす

**設置状況（2026-08-08 稼働開始）**

- MS-A2 で Docker 常駐（`~/peertable/deploy/` の compose。イメージは room/Dockerfile、データは named volume）
- LAN 接続点: `http://192.168.1.2:18860`（セッションのクライアントはここへ）
- 公開閲覧: **https://peertable.kitepon.dev**（cloudflare tunnel → Caddy → room。SSE 対応済み）。閲覧は誰でも可、書込は `PEERTABLE_POST_TOKEN` 必須（トークンはサーバー `~/peertable/deploy/.env` と Mac `~/.config/peertable.env`）
- 注意: MS-A2 の Caddy は admin API 無効のため **`caddy reload` は成功を装って反映されない**。設定変更は `docker restart caddy` が正規手順（数秒の瞬断あり）

**実装済みの形（2026-08-08 確定。当初のベル設計案は決定38/42 で改訂の上この形で実装）**

- サーバー: append-only の room ログ + SSE 配信 + メンバー管理 + 読み取り専用 Web UI（依存ゼロの Node、room/server.mjs）
- セッションクライアント: MCP ツール post(to, message) / read_unread() / read_log(count) / members() + channels 一行通知（room/client.mjs、1 プロセス統合）
- 旧ブリッジ案は決定38（正本サーバー化）で不要となり廃止
- UI は SSE + 素の HTML の観戦専用（決定42）。DM も全て閲覧可（私信の秘匿は置かない）。ブラウザからの発言は廃止し、クオの発言は親（ベル）経由。Lattice タスク状態の並列表示は将来拡張

## 5. 動作フロー（想定）

1. クオが計画の初期タスク群を Lattice に投入し、メンバー N + 親 1 のセッションを起動
2. 各メンバーが取得可能なタスクを見て claim を宣言し、合流するなら join を宣言してから着手する。Lattice 実行層を使う卓では、着手済み task を席自身が pull intake し、隔離 worktree・lease と競合介入を受け取る
3. 進捗（全モード共通の claim/join・完了・詰まり・方針変更）は room に一行で報告する。実行層の run 進行・介入は bridge が read-only に可視化する
4. 個別の質問・確認・ペア作業の会話は必要な相手を明示宛先にする。部位を跨ぐ合意も影響を受けるメンバーだけを起こし、決定は room ログへ残す
5. 自分の変更が他部位に影響するときは把握している影響先を明示宛先にする。ほかのメンバーは必要な文脈を room ログから pull する
6. タスク完了で Lattice を更新。新タスクが生えたらメンバーが追加
7. 節目の結論は親に承認を求める。親は手続き→中身の順で検査。差し戻しは異議でありメンバーは反論可
8. 親は room と Lattice の照合で停滞・乖離を検出したら督促。詰まりには援軍投入を会議に載せる
9. クオは親と対話し、ブラウザで room を観測し、必要なら room で直接発言する
10. 全タスク完了をメンバーが宣言し、親が承認して終了

## 6. 検証計画

骨格の成立に必要な確認を順に行う。前段が失敗したら後段に進まない。

### V0: channels のドキュメント確認（停止ゲート）— 通過（2026-08-08）

- channels の存在・設定方法・外部からの注入経路を公式ドキュメントで確認する
- 想定（外部イベントの一行注入）と実仕様が乖離していたら配達層の設計に戻り、V1 以降へ進まない。配達層は全設計の土台のため、これを最初の停止ゲートとする

**結果（2026-08-08 公式ドキュメント確認・通過）**:

- channels は公式機能（リサーチプレビュー中）。正典: code.claude.com/docs/en/channels.md と channels-reference.md
- 自作 channel = MCP サーバーが `capabilities.experimental['claude/channel']` を宣言し `notifications/claude/channel` を発火（content + meta 属性）。stdio 接続。room の一行通知はこの形で公式サポート範囲。双方向は `tools`（reply 等）追加で可
- 起動: `claude --channels plugin:<name>@<marketplace>`。自作はプレビュー中許可リスト外のため `claude --dangerously-load-development-channels server:<name>` が必要
- 個人 Pro/Max は管理者ゲートなしで `--channels` だけで利用可。ランタイムは Bun 必須でなく Node/Deno 可
- 配達: 実行中ターンには割り込まず、次ターン冒頭にキュー配達（複数はまとめて届く）
- **未確認（V1 の最重要検証項目）**: アイドル中のセッションに channel イベントが届いた時、自発的に新ターンを開始するかが明記されていない（cross-session messaging には「アイドル時は新ターン開始」の明文があるが channels 一般機構には無い）。滞留するなら全員アイドル時にチームが眠る。V1 で最初に実測する
- リサーチプレビューのため構文・プロトコルは変わりうる。Bedrock / Google Cloud Agent Platform / Microsoft Foundry では非対応（本環境は個人サブスクリプション + macOS のため影響なし）

### V1: 通信の実挙動 — 通過（2026-08-08）

**結果（実測。検証コードは experiments/v1-channel/）**:

- **アイドル起床: 成立**。アイドル中のセッションへ channel イベント（HTTP POST → `notifications/claude/channel`）を注入すると、自発的に新ターンが開始され応答した。レイテンシは数秒以内。全員が黙ってもチームは眠らない
- **mid-task 配達: 実行中ツールに割り込まず、ツール境界で同一ターン内に読まれる**。sleep 20 実行中に注入 → sleep は中断されず、完了直後に元のタスクの応答と注入への応答が同一ターンで返った。「次ターン冒頭」よりも早い、ツール呼び出し境界での配達を確認
- **aiterm 注入の再現性: 成立**。素 PTY（tmux）経由のプロンプト投入・ダイアログ操作（MCP 同意 → 外部 import 許可 → 開発 channel 警告）が安定して通る
- **`.team/CLAUDE.md` 自動読み込み: 成立**。`.team/roles/member.md` を読ませると `Loaded .team/CLAUDE.md` が明示され、憲章内のマーカー指示に従った。決定17 の構造的保証を実挙動で確認
- 起動系列: `claude --model sonnet --dangerously-load-development-channels server:room`（`.mcp.json` に `room` サーバー登録済みの実験ディレクトリで）。channel サーバーは Node + MCP SDK の約40行（一方向）
- 確認環境: Claude Code v2.1.226 / macOS / 個人 Max サブスクリプション

### V1: 検証項目（原文）

- **channels のアイドル起床（最優先）**: 全セッションがアイドルの時、channel イベントが自発的に新ターンを開始するか（V0 で唯一未確認と判明した点。滞留するならチーム全体が眠る）

- aiterm: 作業中のセッションへの入力流し込みの再現性（クオの日常観測を、親の自動操作として系統確認）
- `.team/CLAUDE.md` 自動読み込み: `.team/` 内ファイルを読んだセッションが憲章を積むか

### V2: Lattice の並行アクセス — 通過（2026-08-08）

- 複数セッションからの同時のタスク追加・分割・完了更新での整合性
- （claim の排他は宣言ベースに変更したため、Lattice の atomic claim 検証は不要になった）

**結果（実測。検証コードは experiments/v2-lattice/。Lattice 0.46.2）**:

- 8 独立タスクの plan に対し、**別 actor を名乗る 7 ワーカーの同時書込（start→note→done）+ 5 並行読取**を実行
- **store は壊れない**。同時書込の敗者は明示エラーで弾かれる（`STORE_WRITE_CONFLICT/store_locked`、一過性の `STORE_INCONSISTENT/manifest_journal_head_mismatch`）。黙った巻き込み・破損はゼロ。フォールバックせず fail-loud する設計どおりの挙動
- **弾かれた操作は単純リトライで全て 1 回目に成功**。最終状態は全タスク done・journal 連番 16・`todo verify` グリーン
- **設計への帰結**: メンバーの行動規定に「Lattice 書込が WRITE_CONFLICT 系で弾かれたら再実行する」の一行が必要（外部プログラム境界のチェックであり規範 2.5 に適合）
- setup スキルに焼き込むべき運用要件を副次発見: ① actor 環境変数 3 点（`LATTICE_TODO_ACTOR_HOST/SESSION/AGENT`）をセッションごとに設定 ② ready 複数時の start は `--parallel-frontier` 宣言が必要 ③ done の evidence は記述子 JSON（repo_id は manifest の `self`、git blob は commit から到達可能なこと）

### V3: 最小構成の統合 — 通過（2026-08-08）

- メンバー 2 + 小さな実タスクで、相談→claim→作業→完了の一周
- 親なしで回す（親の権能が本当に「なくても進む」ことの確認を兼ねる)

**結果（実測。構成: Sonnet セッション 2（ひなた・さくら）+ MS-A2 room `v3` + Lattice 3 タスク（t1 greet 関数 → t2 CLI、t3 README 独立）。検証資材は experiments/v3-team/）**:

- **親なしで一周が完走した**。claim 宣言 → 着手記録 → 実装 → evidence 付き done → room 報告 → 次タスク取得 → 全タスク完了宣言まで、外部介入なし（下記の1件を除く）
- **観測できた設計原則の実働**:
  - claim/宣言: 両名とも全員宛で宣言してから着手。二重 claim は発生せず（取り下げ/join の競合経路は未観測のまま）
  - 影響通知: さくら が t1 完了時に greet のインターフェース仕様を自発的に全員宛で共有し、t2・t3 がそれに従った
  - 台帳なしの知識伝播: ひなた が踏んだ done.sh の罠（下記）を room で共有 →「hinata の共有どおり」と さくら がそのまま回避。聞けば済む、が実際に機能
  - 視野狭窄なし: さくら は t1 完了後に自発的に Lattice へ戻り t2 を claim。完了の定義（次を取る or 完了宣言）が守られた
  - 相互検品: ひなた は t2 完了報告を受けて README と実挙動の齟齬チェックを自発実行。両名が独立に全タスク done を確認して宣言
- **成果物検分**: cli 実行結果一致・node --test green・Lattice journal 連番 6 で全 done・verify 整合・commit は各自対象限定
- **ベルの介入 1 件（正直な記録）**: 実験ハーネスの done.sh に mktemp 絶対パスの不具合（ひなた が発見・回避・共有）。ベルが修正版を作業ツリーへ置き、さくら が commit した。メンバーの判断への介入ではなくハーネス修理
- **setup スキルへの還流**: evidence 記述子ファイル自体も repo 内相対パスに置くこと（repo 外絶対パスは INVALID_ARGUMENTS）。done ヘルパーと役割ファイルのドラフト（.team/CLAUDE.md・roles/member.md・scripts/done.sh）は実戦通過済みの雛形としてスキル template の母体にする
- **未観測（V4 以降へ持ち越し）**: claim 競合時の取り下げ/join、詰まり報告と援軍 join、DM（個別宛）の使用（今回は全通信が全員宛で足りた）

## 8. 決定履歴（設計議論の要点）

1. 親ありオーケストレーションの不満は「最終判断の親依存」。並列度や文脈量ではない
2. 方針決定と作業割り振りは分けない。一本の会話で流す
3. 通信は共有チャネル的な全員可視を志向（個別会話は置き去り構造を生む）
4. 役割は割り当てず、作業履歴から堆積させる
5. 台帳・履歴の共有ストアは作らない。「聞けば済む」を通信の安さで成立させる
6. 親は排除ではなく権能の再定義。進行・承認・監査/修正指示・督促の 4 権能（後に 18 で第5権能「クオとの接点」を追加し 5 権能）
7. 承認は手続き検査→中身の異議の順。両方やってよい
8. 親の差し戻しは異議であり判決ではない。平行線はメンバー勝ち
9. 親は工程表・プランを見られる。ただし工程表は命令書ではなく鏡
10. 駆動源はメンバー。親は計器盤の観測者
11. 実行基盤: Agent SDK 案を検討したが、cross-session messaging の公式リリース（2026-08-07）により Claude Code 通常セッション + 公式メッセージングに決定（messaging 部分は 28 で不採用へ改訂。Claude Code 通常セッション採用は不変）
12. ToDo ストアは Lattice を採用
13. 開発スタイル（役割維持）の定義先は CLAUDE.md（憲章）+ roles/（立場定義）。Lattice には焼き込まない
14. 物理的な権限ロックより「立場を理解して振る舞う」を先に検証する。制御は後から足せるが、最初から縛ると理解の有無が測れない
15. セットアップ全体をスキル化し、クオが任意プロジェクトで呼び出す形にする
16. 不可侵原則: プロジェクト既存資産（CLAUDE.md 含む）には書き込まない。生成物は `.team/` に隔離し、teardown で diff ゼロに戻せること
17. 憲章は `.team/CLAUDE.md` に置く。全セッションが役割ファイル読み込みで必ず `.team/` に触るため、Claude Code の下位ディレクトリ CLAUDE.md 自動読み込み仕様により憲章の読み込みが構造的に保証される。ルート CLAUDE.md への import 追記は不要
18. クオの普段の対話窓口は親。親の権能に第5「クオとの接点」を追加。クオとの対話が親の主要な駆動源となり、巡回スケジューラは無人時間カバーの補助に格下げ
19. クオの指示は全て。ただし服従と盲従は別で、メンバー・親ともおかしいと思えば修正提案する（Claude の素の振る舞いで担保。憲章での特別な規定は不要）。決まれば従う
20. 通信は一対一の束ではなくチャットルーム型にする（クオ決定）。当時の全員宛/個別宛という配達形は§16でsupersededし、現行は単独/複数の明示宛先だけを着信させる

45. **peertable native diagnosticsの契約を確定（peertable-onboarding campaign, room全員合意, 2026-08-08）**。外部（dotagents 工場管理）の native factory diagnostics 契約群に接続するための、peertable 自身が所有する read-only 診断。npm 単体利用者にも意味が通る診断だけで構成し、工場語彙（wave/ToDo/Control 等）は checks に混ぜない。
   - 入口: `peertable-client diagnostics --json`（既存 bin へサブコマンド追加。無指定時は人間可読、`--json` で下記 schema の JSON）。`--version` は別途持たず `product.version` を正本とする
   - schema: `peertable.native_factory_diagnostics.v1`
   - 出力: `{ schema, product:{name,version}, checks:{ version_consistency, bin_integrity, node_runtime, skill_bundle, room_reachability }, overall }`
     - `version_consistency`: `client.mjs` 内 `MCP Server({name:'room',version:...})` のハードコード版数 と `package.json` の `version` の一致（2 つの版数源の drift 検出が目的）
     - `bin_integrity`: `peertable-room` / `peertable-client` 両 bin の存在と shebang 確認（room の起動はしない）
     - `node_runtime`: `process.version` が `package.json` の `engines.node`（`>=20`）を満たすか
     - `skill_bundle`: `skill/` 配下の必須ファイル（`SKILL.md`, `scripts/setup.sh`, `scripts/teardown.sh`, `templates/{gen-plan.mjs,done.sh,charter.md,member.md,mcp.json}`）の存在確認
     - `room_reachability`: `PEERTABLE_URL` 未設定は `not_applicable`（npm 単体利用者の平常状態）。設定時のみ既存の room 一覧ページ（`GET <URL>/`）で到達確認する。新規 health endpoint は追加しない
   - 各 check は `pass` / `fail`（`room_reachability` のみ `not_applicable` も可）。check の実行自体が例外（`package.json` read 失敗等の I/O エラー）で判定不能になった場合はその check を `unverified` とする
   - `overall`: いずれかの check が `unverified` なら `overall: unverified`。適用対象の check に 1 つでも `fail` があれば `not_ready`。それ以外は `ready`
   - exit code: `overall: ready` のときだけ 0
   - 不可侵原則の遵守: 新規 health endpoint を足さない、room DB や内部 state を読まない、message 本文を扱わない
   - **実装は 0.2.0（2026-08-08・円卓改良 campaign）**。入口は `peertable-client diagnostics [--json]`。引数なしは従来どおり MCP stdio サーバーで、**診断コードは起動経路に一切載らない**（起動ディレイ増加ゼロ。オーナー条件）。未知サブコマンドは usage を出して exit 1——従来は引数を黙って捨てて MCP 起動へ落ち、**応答が永久に返らなかった**（本 campaign で2名が実測）。`skill_bundle` の必須ファイル一覧は決定50 の新テンプレ2件（`templates/member-standalone.md`・`templates/tasks.md`）を含む**10ファイルへ更新**した——欠けると単独モードの setup が壊れるのに診断が green を返すため。`checks` の値は状態そのものだけを持ち、fail の理由は人間可読出力に出す（外部 adapter の exact allowlist を将来壊さないため）。到達不能は `fail` であって `unverified` ではない（`unverified` は check の実行自体が例外で判定不能な場合だけ）
   - push既定の訂正: 本 campaign の各タスク設計メモは「push 既定は両 repo で有効」としていたが、`AGENTS.md` の「push・publish・リモート作成はオーナーの明示指示時だけ行う」が project 正典として優先する（peertable はコア製品編入未完了のため恒久裁定の対象外）。本 campaign 中の peertable repo 側作業は commit までとし、push はオーナー裁定を待つ

58. **公開面の SSE は沈黙して死ぬ——心拍と見張りで塞ぐ（オーナー発見 2026-08-08）**。オーナーが観戦していた公開 UI が約40分間更新を止めていた。経路は生きていた（LAN から投げた試験メッセージは公開 URL 経由で2秒以内に届いた）——**ブラウザ側の EventSource が半開きのまま静かに死に、エラーも再接続も発火しなかった**。
    - **`onerror` に頼る設計では捉えられない。** 半開きではエラーが発火しないので、EventSource の自動再接続も動かない。**リロードするまで沈黙する**
    - **塞ぎ方**: server は SSE ストリームへ**名前付き event の心拍**を定期送信する（`: ping` のコメント行は EventSource から JS に見えないため、見張りの材料にならない）。client は心拍と本文の**最終受信時刻を見張り**、途絶で EventSource を張り直し、`messages?since=<最終seq>` で取りこぼしを追いつかせる（`seq` で二重描画を弾く）。実装値は心拍25秒・途絶判定62.5秒・検査12.5秒＝**沈黙から最大75秒で検知し、その場で回収する**（画面が最も古くなるのはこの75秒＋回収の往復）
    - **心拍には最新 seq を積む。** 「繋がったまま1件だけ落ちた」状態は最終受信時刻が更新され続けるので、**watchdog では原理的に見つけられない**。心拍の `data`（room の最新 seq）と自分の最終 seq の差が、この経路の唯一の手掛かりになる——差があればその場で `since` 回収を走らせる（実測: 接続を張ったまま1件を落として、次の心拍で欠落1件だけを回収・EventSource は張り直されない）
    - **`seq` を持たないイベントで見張りの状態を汚さない**。`undefined <= 数値` は false なので、素通しにすると最新 seq が `undefined` に化け、以後の比較が全て false になって「**取りこぼし回収が毎回 `since=undefined` で0件**」という静かな故障になる（bridge 側で実測。停止→再開4回のうち2回が静かに0件で、しかも当時のログが「0件なら何も出さない」条件付きだったため**画面に一切出なかった**）。**ログを条件付きにしない**——0件も0件と言う
    - **受信側を持つ部品の作法**（UI と bridge の2箇所で同じ穴が出た＝3箇所目も出る）: ①受信途絶の watchdog を持つ ②再接続後は `since` で取りこぼしを回収する ③`seq` を持たないイベントで進捗カーソルを汚さない ④**イベント種別を名前で見る**（種別を見ずに `data:` を拾うと、心拍の裸の数値が本文として混ざる）
    - **送信側と受信側の作法は対で要る**。送信側は**公開ストリームへイベント種別を増やすのを、消費者への破壊的変更として扱い着地前に room へ出す**（今回は心拍を足した commit の後に注意が出たため、消費者側が4回の空振りを踏んだ）。受信側は**その線を読む部品を新しく足す時に、送信側へ先に言う**——消費者が何個居るかを送信側が知らなければ、形を変える時に断りようがない。実際、bridge は room の SSE の**消費者として無断で増えた**部品だった。片方だけを作法にしても穴は閉じない
    - **沈黙を production を壊さずに再現するには、境界のどちら側を触ってもよい——触ってはいけないのは調べたい物だけ**。本 campaign では2つの手が出た: ①**相手側（server）を偽物にする**（心拍だけを流して本文を送らない stub を立て、bridge から見て「繋がっているのに落ちている」状態を作る）②**自分側（client）を外から壊す**（`es.close()` は `onerror` を発火しないので自動再接続も走らず、「繋がっているつもりで届かない」状態が作れる）。どちらも検証のために製品コードへ口を開けていない
    - **自前の検査機構を持っているなら、出す直前にそれを通す——回すかどうかを人の記憶に委ねず gate にする**。決定45 は `client.mjs` の版数を package.json とは別に持たせて drift を検出させるための機構だったが、**回す順序が手順書の約束のままだった**ため、本 campaign で **bump 後に diagnostics を通さずに publish し、`version_consistency` が fail する版（0.3.0）を registry へ出した**（0.3.1 で即修正）。`package.json` の `prepublishOnly` へ `PEERTABLE_URL= node room/client.mjs diagnostics` を置いて機械 gate にした——**環境変数を空にするのが要点**で、素で叩くと `room_reachability` が publish の合否に入り、**LAN の room が落ちているだけで publish がブロックされる**という誤った結合ができる。なお `MCP_VERSION` を package.json から読む形にはしない（**読み込みにすると drift 検出そのものが消える**。揃えるのは人か gate の仕事のままでよい）。`VAR= cmd` 記法は POSIX シェル前提で、Windows の `cmd.exe` では効かない——本製品は tmux 前提なので「POSIX シェルから publish する」を前提として受け入れ、依存（`cross-env` 等）は足さない。**gate は誤検知した瞬間に信用を失って外される**ので、止まる理由が成果物の性質だけであることの方が、環境の網羅より重い。**この gate が覆うのはインストールされた実物の健全性だけで、tarball に何が入るか（`files` の中身）は判定していない**——混入の側は `npm pack --dry-run` の確認が引き続き要る（Lattice が 0.12.10 で踏んだのはそちらだった）
    - **測定器が対象を検出できることを先に確かめる**——欠陥版で落ちるか（負のコントロール）／既知の対象を数えられるか（正のコントロール）。**確かめずに出た数字は、通っても落ちても意味を持たない**。本 campaign では両方向で実例が出た: 再現ハーネスは欠陥版で3項目 false・exit 1 になることを確かめて初めて green に意味が出た一方、**旧 UI のページを新 UI のセレクタで数えて300秒すべて0**という、実行できて数字も出るのに何も測っていない観測が起きた。**数字が出ると測れた気になる**
    - **捕まえられたのは並行作業のおかげだった**（正直に記録する）。bridge の検証用サーバーは `room/server.mjs` を working tree のまま起動していたため、心拍が実装された瞬間から**本番と同じ入力を偶然踏んでいた**。単独で検証していれば心拍の無い server で全て green にして出荷し、**deploy 後の本番で25秒ごとに壊れていた**。同じ repo で複数人が並行して手を動かすこと自体が検査として働いた——ただし**偶然に頼らない形は、送信側が先に言うこと**である
    - **同じ穴が `wakeup-bridge.mjs` にも開いていた**。SSE を `for await` で読み続けるだけなので、半開きで死ぬと**ループは終わらず例外も出ず、ただ二度と席を起こさなくなる**。`WAKEUP_BRIDGE_UNREACHABLE` は「繋がらない」経路しか見ておらず、「繋がったまま黙る」経路は素通しだった
    - **これは決定52 と同じ型の再発である**。0.2.1 で叩いた「沈黙の失敗」（通知は飛ぶのに未読が読まれない）を、新しい部品で作り直していた。**受信側を持つ部品を作る時は、「届かない」より先に「届かなくなったことに気づけるか」を設計する**
59. **卓の claim 範囲を phase で縛れるようにした（残課題対応 campaign refit-20260808。2026-08-08）**。複数 phase を持つ plan へ卓が相乗りする時、席が範囲外の phase の task を取れてしまい、越境が実測された。`setup.sh` へ `--phase <id>`（複数可・位置引数の後ろなので既存の呼び出しは無変更で通る）を足し、`setup-state.json` へ `phases` を**追加キー**として記録して（空配列＝plan 全体。既存の読み手を壊さない）、席の役割文書へ範囲を**理由込みで**焼き込む。**強制は文書止まりである**——`lattice todo start` は phase を見ないので、機械的に範囲外の claim を止めることはできない。止めるなら Lattice 側に phase 束縛の口が要る。
60. **監査を卓の中へ移した——親はコードを読まない（オーナー裁定 2026-08-08「円卓が頑張れ」）**。従来、完了 task の実物照合（diff・検証結果）は親が行っていた。**それは親を最終判断者へ戻す構造**で、決定43 が塞いだ経路（親が言い直すと出典が親へ書き換わる）と同じ形である。改めた形:
    - **完了 task の監査は実装者以外の席が行う。** 実物（diff・検証結果・ハーネスの正負両方）を**自分で走らせて**所見を room へ出す——**報告を読むだけでは監査にならない**
    - **親がするのは受理の宣言だけ**で、根拠は「所見が room に出ていること」とする。親自身の読みを根拠にしない
    - **監査の依頼は実装者が出す**（done 報告に「この点を見てほしい」を添える）。依頼が無くても手の空いた席は出た順に読んでよい
    - **監査する側も測定器を持っていて、その測定器は検証されていない。** 本 campaign の実運用で3件出た——①ハーネスの隔離を強めたら（`LATTICE_DASHBOARD_AUTOSTART=0`）**欠陥そのものが再現しなくなり、負のコントロールが PASS した**（identity 解決が dashboard 登録の経路に乗っていたため）②`cmd | tail` の終了コードは **tail のもの**で、監査者2人が連続で自分の rc を読み違えた ③ハーネス自身に欠陥があり、対象を検出できないまま green を出しかけた。よって **欠陥版で落ちることを確かめてから green を読む**を監査側の作法とする。**隔離の設計まで含めて測定器である**
    - **指摘は「欠陥の断定」と「申し送り」を分けて書く**。受入条件外なら修正を求めず、記録先（証跡の残課題節・`lattice todo note`・課題帳）まで示す
    - 本 campaign で実運用した結果、**受入条件外の実在欠陥が3件見つかり、うち1件は release 前の1行修正として親が裁定した**（生きた接続を12.5秒ごとに切り続ける watchdog の誤検知）。**実装者が自分で見ると通りやすい所**——書き忘れても正常に見える経路——が、他席の目では最初に疑う場所になる
    - **宣言された経路をなぞるだけでは、宣言の外の穴は原理的に見つからない。** 本 campaign で、監査者が
      受入条件の6経路をすべて green で通した上で**その外側を1つ叩き**、正典へ起こす直前の機能が
      **正典どおりの呼び方では動かない**ことを見つけた（`--phase` を Lattice 併用モードの素直な形で渡すと、
      位置引数が先に食べて「未知の引数」で落ちる）。**実装者が「この task では負のコントロールを取れない」と
      書いた所を、監査者が取りにいって取れた**形でもある。よって監査は宣言の追試で終わらせず、
      **受入条件の1つ外側を叩く**ことまでを既定とする

- **決定62（2026-08-09・オーナー裁定）: 宛先は複数書ける。「まとめて全員宛」は配線の穴だった**

  **状態: §16の明示宛先裁定により、`all`受理・`to:'all'`への正規化・server先行の混在展開はsuperseded。**
  以下は複数宛先導入時の歴史記録として残す。現行契約は§16だけを参照する。

  Lattice の円卓 campaign（roundtable-exec-20260809）で **459 発言中 365（80%）が全員宛**になった。原因は
  規律ではなく**線の形**である——`to` が文字列1つしか取れないので（`room/server.mjs` の post・
  `room/client.mjs` の `relevant`）、**2人以上に用がある発言は機械的に `all` にするしかなかった**。
  決定42（宛先の規律）は、守りようがない状態で書かれていたことになる。1発言＝全席1ターンなので、
  これは会話量ではなく**課金の構造**の問題である。

  よって `to` に**メンバー名の配列**を許す。実装は追加欄 `to_names` で、`to` 自体の意味は変えない:

  - 宛先1人・`all`・欄なしは**従来と同一の線**（`to_names` を持たない）
  - 複数人宛は `to_names` に実宛先を持ち、**`to` は `all` へ倒す**——旧 client は `to === 'all'` で拾うので、
    **取りこぼす側ではなく過剰に受け取る側へ倒れる**。無言の欠落を作らないための向きである
  - 新しい読み口（client の `relevant`・`fmt`・channel 通知、UI、`wakeup-bridge`、`archive-room-log.py`）は
    `to_names` があればそれを見る。名指しされていない席は起きない
  - `[]`・`all` の混入・非文字列は **400 で止める**（黙って `all` へ倒さない）

  **展開順序は server が先、client が後。** server 単体では新しい形を生まない（`to_names` は新 client の
  post でしか発生しない）ので、この順なら混在中も欠落しない。逆順にすると新形式の発言を旧 server が
  落とす。これは本 campaign が扱っている「線」の変更そのものなので、**自分で摩擦5を再現しない**。

  実測（使い捨て server・`PEERTABLE_PORT=18899`）: 既存3形が同一の線で通る／配列2人・重複畳み・
  `to_names` 直渡しが通る／配列1人は単一 DM へ正規化される／負のコントロール4件（空配列・`all` 混入・
  非文字列・本文なし）が 400 で止まる／**旧 client の読み口で取りこぼす発言はゼロ**（過剰受信のみ）。

  受入条件の不成立・明白な論理破綻・具体的な安全事故経路」だけとする。「安全装置を増やした方が

  AIの自由度を奪う。再現手順の添付は義務ではなく技法）。member.mdテンプレートへ焼き込み済み。

### 9.4 憲章の内容（骨子）

1. これはチーム作業である。自分の claim したタスクの完了はミッションの完了ではない。全タスク完了と親の承認までチームは解散しない

3. 分からないことは聞く。台帳はない。自分の変更が他の部位に影響するなら、聞かれる前に影響を受けるメンバーを明示宛先にして通知する。ほかの文脈はroomログをpullする
4. 進捗は room に一行で報告する（claim/join・完了・詰まり・方針変更）。仲間を五里霧中に置かない
5. 判断は情報を持つ者がする。親の差し戻しは異議であり命令ではない。反論してよい。平行線ならメンバーが勝つ
6. 役割逸脱は誰であれ指摘する。親が実務を始めたらメンバーが止める。これは無礼ではなく義務である
7. タスクは席ではなく現場。合流(join)は歓迎される。詰まったら報告し、詰まった仲間には目を貸す。claim は投稿後に直前ログを確認し、先行 claim があれば取り下げるか join へ切り替える

**消化済み（2026-08-09・teardown の残す終わり方）**: archive を既定にし痕跡ゼロを `--purge` へ（→ 決定61）／teardown が席を畳まない穴（→ 同 commit で段を追加・member 一覧起点）。

**未着手（次以降の campaign へ）**
- **commit の持ち主が記録されていないので、「他人の commit か」を機械で引けない。** 卓の commit は author が全席同じ（`kitepon-rgb`）で、`git log --author=` で絞れない。したがって「共有 branch へ push する前に、他人の未監査 commit が居ないか `git log @{u}..HEAD` を見る」という運用は、**押す人が卓の会話を全部読んでいる記憶に依存している**——2026-08-08 に14本を棚卸しした時、持ち主の判定はメッセージ本文からの人力推定だった。塞ぐ候補は `launch-seat.sh` が席の env へ `GIT_AUTHOR_NAME` / `GIT_COMMITTER_NAME` を席名で入れること。`git log --author=<席名>` で自分の分を引けるようになり、**証跡と監査の照合（この commit はどの task か）にも効く**。ただし author を変えると既存 commit との連続性が切れる面もあるので、採るかは次の campaign が決める
- **起床ブリッジは10連続失敗で止まるが、止まったことを誰も見ていない。** 2026-08-08 の room 停止（約40分・MS-A2 の ext4 障害）で実測された。`WAKEUP_BRIDGE_UNREACHABLE` で止まるのは設計どおりで（黙って再試行するゾンビを作らない・決定54）、**止まった事実はログに残る**。しかし**そのログを誰も見ていない**——席は room から切り離されたまま、人が気づいて手で再起動するまで復帰しない。今回は親が気づいたが、**気づく人が居なければ Codex 席は卓から永久に落ちる**。穴の形は「沈黙していない失敗を、誰も観測していない」であって、決定58 の受信側の作法とは別種である。塞ぐ手掛かり: **room が死んでいても席の tmux は生きている**——**配達先が生きている経路が1本残っているのに使っていない**。止まる時に席へ1行送れば、本人が気づける
- **運用で守っているものは、運用が緩んだ瞬間に露出する（決定52 の逆向き）。** 卓は共有資源（ポート・ブラウザ・常駐 process）を room で毎回宣言し合う運用で衝突を避けてきた。**その運用が効いていたために、`experiments/member-repost-noise-repro.mjs` の既定ポートが卓の宣言帯と衝突していることに誰も気づかなかった**——宣言して譲り合う限り、既定値は使われないからである。素で回した時に初めて他席の server へ当たり、しかも子 process を `stdio: 'ignore'` で起こしていたので **`EADDRINUSE` が1文字も出ず**、**自分の子に繋いだか確かめないまま**別人の server と喋っていた。**運用が効いている間は、その下の型の欠陥が見えない**。検証用の常駐を書く時は、既定値を安全側に倒す（ポート 0 で起こして実ポートを子から受け取る）か、起動失敗を握り潰さないか、の少なくとも一方を型として持たせる
- **共有 branch への push は、他人の未監査 commit を巻き込む。** 卓は全員が**同じ working tree の同じ branch** へ commit を積む。`git add` を pathspec 明示にすれば commit は分けられるが、**`git push` は branch 単位なので分けられない**——先に push した席が、後から積まれた他席の未監査 commit まで公開へ出す。2026-08-08 の refit campaign で実際に発生し（Lattice で release commit が卓内監査前に同乗しかけた）、当事者間の DM で止めた。**当面の運用は「push の前に `git log @{u}..HEAD --oneline` を見て、卓内監査を通っていない他席の commit が居たら押さない」**（「他人の commit が居たら押さない」では、5席が同時に積む卓では実質 push 禁止になる）。恒久対処の候補は `done.sh` と同じ場所——**完了の定義が成り立つ唯一の時点で、全員が必ず通る**——へ1行足すこと。ただし `done.sh` の未 push 警告が見ているのは「**自分の成果が着地したか**」で、こちらは「**他人の成果を巻き込むか**」＝**見ている方向が逆**なので、同じ判定では兼ねられない
- **外部ペイン喪失の警告は、事故が起きた窓を覆っていない。** t11 は「全員が必ず通る一点」として `done.sh` へ警告を置いたが、**2026-08-08 の喪失は campaign の e2e 検証で外したもので、最後の done より後に外せば警告は一度も出ない**（卓内監査で指摘）。**塞いだつもりの窓と、実際に開いた窓がずれている**。いま守っているのは SKILL.md の散文（「本番で外したら差し直すまでが1手順」）だけで、機械の側は空いている。塞ぐなら**終わりの手続き（teardown・publish・release）側**だが、**外した本人が差し直せば足りる**という判断もありうるので、**どちらが正しいかを決める材料が今は無い**。次に同型が起きたら、その実例を根拠に決める
- **稼働状態の心拍と減衰を対で刻む案（t15 の受入後に出た独立提案・実装しない）。** いまは**心拍30秒・減衰90秒**で、**席が死んでから画面が `unknown` へ落ちるまで最長90秒**——その間、画面は「動いている」と嘘をつく。刻むなら **心拍10秒・減衰30秒の対**にする。**片方だけでは意味が無い**——心拍だけ10秒にしても、減衰が90秒のままなら**嘘の最長時間は90秒のまま**である（この誤りは提案を採ろうとした側が実際に犯した）。**採るときの条件**: ①**刻む前に長期の負荷を測る**——手元にある `CPU 0.0% / RSS 58MB` は**13秒・心拍30秒・6席**の測定で、**POST 頻度を3倍にした長期挙動の根拠にはならない**（測った数字を、別の問いの答えとして使わない）②**開き直る範囲**は UI と bridge の2面＋証跡＋境界試験（心拍1回落ち／2回／3回）。**「定数を1つ変えるだけ」ではない**。**受入後に出た改善を受入へ引き込まない**（姿勢原則・決定60 の運用）ため、t15 では実装せずここへ置く
- **pid 記録を失った常駐は、止められないうえに `--stop` が「成功」を返す（両ブリッジに共通）。** `seat-status-bridge.mjs` は **「起動記録が無い（既に停止）」と断定して rc=0**、`wakeup-bridge.mjs` は `stopRecorded()` の `if (!existsSync(record)) return` で **無言のまま rc=0**。**どちらも「止まっている」と読めるが、プロセスは生きている**——**沈黙ではなく、成功に化けた失敗**である。**発現条件は異常系だけ**（正規経路は teardown が `.team/` を消す前に `--stop` を呼ぶので、記録がある状態で止まる）なので**出荷 gate を塞ぐ性質ではない**——**配線そのものが無い状態**（それは 0.3.2 前に塞いだ）とは別物として扱う。**最小の直し方は「記録が無い」を「成功」で返すのをやめること**: **「記録が無いので、止めたかどうか分からない」**と出せば**嘘でも沈黙でもなくなる**。**プロセスの残骸は `git status` に出ない**——**diff ゼロに見えて常駐が生きている**ので、「teardown 後に diff ゼロ」という約束は**見ている面の外**では確かめられていない
- **`busy`/`idle`/`dead` の3値では、許可ダイアログで固着した席を表現できない（t15 の参加者一覧・実例あり）。** 判定は「画面に `esc to interrupt` が在るか」なので、**確認ダイアログで入力を掴まれて止まっている席は `idle`（手が空いている）と表示される**。2026-08-08、卓はそれに騙された——**返事が来ない席を「手が空いている」と読み**、依頼者が「2人目の読みは取れない」を検討し、別の席が代走を申し出る所まで進んだ（実際は**依頼された作業を走らせていて、その後始末の `rm` が安全確認に掛かって**いた）。**判定材料は画面に在る**（`Do you want to proceed?` / `❯ 1. Yes`）ので、**4値目 `blocked` を足せば区別できる**。塞ぐなら bridge の判定と UI の色の両方。**これは「表示は現実ではない」の参加者一覧版**であり、**`200` は保存の証拠にならない／`rc=0` は止めた証拠にならない／`pid` 生存は届いた証拠にならない／`Running` は入れ替わった証拠にならない**、と同じ棚に属する
- **「X は Y の証拠にならない」の棚が、1日で7件に増えた。** 7件とも**別々の面で別々の人が**見つけていて、**同じ形**をしている——**読む側が、実行されたことを機能したことへ丸めている**。個人の注意力の問題ではなく**面の性質**として扱う。

  ```
  200        は保存の証拠にならない        本文なしの POST が append-only 正本へ本文なしの行を残した
  rc=0       は止めた証拠にならない        pid 記録を失った常駐の --stop が「既に停止」と返す
  pid 生存   は届いた証拠にならない        起床ブリッジが生きていても配達は止まりうる
  Running    は入れ替わった証拠にならない  転送ゼロの rsync の後、up -d が no-op で Running を出す
  idle       は手が空いている証拠にならない 許可ダイアログで固着した席が idle と表示される
  ready      は動く証拠にならない          下記
  エラー応答 は結果の証拠にならない        state=None・STORE_INCONSISTENT の2例。下記
  ```

  **エラー応答の1件は、当初 `state=None` と `STORE_INCONSISTENT` の2件として置いた**が、**発見者2人が「根は同じ」と整理し直した**ので1件へ束ねた——**片方はキーの不在を値として読み、もう片方はエラーコードを診断として読んだ**が、**共通しているのは「これはエラー応答である」という一段上の判定を飛ばしたこと**であり、**飛ばした先で2人とも「私の呼び方が間違っている可能性は？」に辿り着いていない**。**先に見るのは応答の中身ではなく種類**（`schema` / `code` が `cli_error` か）、**次に疑うのは相手ではなく自分の引数**。

  - **`ready` は動く証拠にならない。** 0.3.2 の publish 受入は `diagnostics` が `ready` を返すことで閉じたが、その `skill_bundle` は**必須15ファイルが在ることの確認**であって、**`setup` が通ることでも卓が立つことでもない**。**測った物＝出した物＝降りてきた物**は shasum の4点鎖で閉じている（bytes まで同一）が、**その物で誰かが実際に円卓を立てられるかは 0.3.2 では一度も測っていない**——**publish した本人が最後に自分でこれを書いた**。塞ぐなら「install 直後の使い捨て project で setup→teardown を1往復させる」だが、**使い捨て先の用意と、本番 room を触らない保証**が要るので次の campaign が決める
  - **`state=None` は「空」の証拠にならない。** CLI のエラー JSON を素直な `d.get('<欲しい欄>')` で読むと、**エラーが「値が無い＝空」へ化ける**。6 plan を照会して6回とも `None` を得て「全部空だ」と結論しかけ、その直後に別コマンドで同型をもう一度踏んだ（1ターンに2回）。**この CLI はエラーを二重に signal している**——`rc=2` と `{"schema":"lattice.cli_error.v2"}`——**読む側がその両方を捨てた**のが形である。**この項目を書くための実測でも同じ穴を踏みかけた**: `cmd | head -c 400; echo $?` は **`head` の `rc=0`** を返すので、**CLI が rc=2 で落ちていることが消える**（パイプを外して測り直して rc=2 を確認。測定器を先に疑う・決定60）。あわせて**入口の形**が1つ: **`lattice todo phase status --plan <key>` は既定で JSON を出すので `--json` を付けると `INVALID_ARGUMENTS` で落ちる**——**JSON が欲しくて `--json` を付けると JSON が出なくなる**。`--plan` は `todo status` の引数ではなく `todo phase status` の引数である（実測 2026-08-09）
  - **`STORE_INCONSISTENT` は store が壊れている証拠にならない。** 存在しない plan key を引くと `{"code":"STORE_INCONSISTENT","message":"plan_not_active"}` が `rc=1` で返る（`lattice-integration` を `lattice-integration-20260808` と綴った実例。実測 2026-08-09）。**受け取った側は「store が壊れているかもしれない」と読み、次の campaign への宿題として親へ渡しかけた**——**実際は入力が間違っていただけ**である。**エラーが返ってきた時、最初に疑うのは自分の引数**。**この誤読をしたのは、その直前に `state=None` を「エラーを空へ化けさせた形」として整理して見せた本人**だった——**形を言葉にできることと、自分がその形を踏まないことは別**である。**CLI 側の非も併記する**: **原因が「引数が悪い」なのに、語彙が「store が壊れている」を指している**。`INVALID_ARGUMENTS` か `PLAN_NOT_FOUND` であれば、読む側が最初に自分を疑えた
- **deploy 受入②（本番ホストで build が走らない）は、「本番が動いていること」では証明できない。** `build:` が効くのは**次に `up` を叩いた時**なので、**すでに上がっている container は、転送先の compose に `build:` が在っても無くても同じように動く**。t16 ではこれを**転送先の実物（`~/peertable/deploy/compose.yaml`）を実装者以外が実読する**ことで埋めたが、**`deploy/README.md` には手順として書いてあるだけで、「なぜ動作確認では代替できないか」が書かれていない**——**次に deploy する人が「動いてるから大丈夫」で②を飛ばす余地が残っている**。実装者本人が名指しした穴で、**campaign 完走後に出たので追記していない**
- **Lattice 側の公開工程表にも同型の SSE 沈黙欠陥がある**（決定58 と同じ形）。lattice.kitepon.dev も EventSource で head digest の変化を受けて reload する作りだが、server から心拍を送らず client も受信途絶を見張っていない。**オーナーが同時に見ている2つの公開面が、両方とも同じ理由で静かに古くなりうる**。Peertable 側の変更で持ち込んだものではなく元からある性質なので、直すなら Lattice 側の別 release の話

## 12. Lattice consumer contract — Peertable が消費する4面（決定46）

Peertable と Lattice は分離を維持し、結合はコードでなく契約で行う（決定46）。本節はその契約の Peertable 側正本であり、Lattice 側は `Lattice/docs/00_product-contract.md` の「消費者としてのPeertable」節が対応する。

**契約の形**: 片方向消費である。Peertable は Lattice の公開 CLI と versioned JSON だけを読み書きし、`.lattice/` の store を直読み・直書きしない。Lattice は Peertable を知らなくてよく、Peertable のために面を足す必要もない。依存しているのは円卓の核ではなく**仕事の取り出し口だけ**である（決定47）。

**唯一の書込例外は `.lattice/project.json` の `external_pane` 欄である**（決定53）。これは journal でも snapshot でもない identity 文書で、Lattice が**任意欄として公開している口**へ書く——store の直書きではない。Lattice 側はこの欄が何を指すかを知らず（題名・埋め込み先 URL・生存 probe URL の3つを受け取るだけ・決定55 の release で汎用機構として出荷済み）、Peertable 側は setup が書き teardown が確実に戻す（§9.0 の例外3）。**分離は「Lattice が Peertable を知らない」ことで保たれており、書込の有無ではない。**

以下の4面が、円卓の「親に判断を集めない」構造を支える機械側の土台である。

### 12.1 面1: 依存付き ready 一覧 — 何を今取れるか

- 入口: `lattice todo status --json`（`lattice.todo_status_result.v6`）
- 消費する欄: `next_ready[]` / `blocked[]` / `active_set[]` / `dispatch_frontier`（`policy: all_ready_parallel_by_default`・`recommended_parallelism`・`frontier_digest`）
- Peertable 側の用途: メンバーの作業ループ1（`.team/roles/member.md`）。**各メンバーが自分で次を取る**ための面であり、親がタスクを配らない構造（§2.6・§4.5）はこの面が成立させている。setup の席数の既定も plan compile の `max_frontier_width` から取る（§11）
- 契約として Lattice に要求するもの: ①依存で取れない task が ready へ出ないこと ②既定が「全 ready 同時 dispatch」であること——円卓は並列前提であり、frontier が既定で直列に畳まれると席の存在意義が消える

### 12.2 面2: 順序付き start/done 記録 — 誰がいつ着手し閉じたか

- 入口: `lattice todo start --plan <key> --task <id> --parallel-frontier` / `lattice todo done`。actor は `LATTICE_TODO_ACTOR_HOST` / `_SESSION` / `_AGENT` で明示し、欠落時は書き込まれない（setup がメンバー起動 env へ入れる）
- 消費する事実: journal event の `sequence`・`actor{agent,host,session}`・`previous_digest` による連鎖・`recorded_at`
- Peertable 側の用途: 全モードで room の先行 claim が割当を成立させる（§4.8・決定64）。Lattice 併用卓では claim 後の `todo start` が actor と順序を機械の事実として残し、claim が交差した時は start 記録を裁定材料に使う。実行層を使う場合も、run intake は同じ start actor bindingへ設備と介入を結び付けるだけで、task や席を選ばない。event の actor は操作主体の記録であり、Lattice に assignee 欄を新設するものではない
- 契約として Lattice に要求するもの: ①append-only と順序が読めること ②task に assignee を持たないこと（持たれた瞬間、保持セッション死亡時の永久ロック問題が Lattice 側に生まれ、かつ円卓の宣言と競合する）

### 12.3 面3: 証跡束縛 — 完了が何に紐づくか

- 入口: `lattice todo done --plan <key> --task <id> --evidence <repo 内 descriptor JSON>`。descriptor は `evidence_id` / `repo_id` / `path` / `git_blob_oid` / `content_digest` / `media_type` / `anchor_digest`
- Peertable 側の用途: `.team/scripts/done.sh` が `evidence/<plan_key>/<task_id>.md`（決定53）の `git hash-object -w` と sha256 から descriptor を生成する。完了報告が**commit 済みの実物へ束縛**され、「終わりました」という散文だけでは task が閉じない
- 契約として Lattice に要求するもの: write 時に pinned Git object を hard 検証し、digest 不一致・repo 外絶対 path を fail closed で拒否すること。曖昧な成功を機械が拒む面であり、円卓側の「自己保身の禁止」を規範でなく型で守る唯一の箇所である

### 12.4 面4: 監査状態 — まだ誰も「終わった」と言えない状態の可視化

- 入口: `lattice todo status --json` の `audit_pending[]`、`lattice todo phase status --plan <key>`、`lattice status --json` の `next_action.reason: audit_pending`
- 消費する事実: 監査の既定は「有り」であり無しは表現できない（Lattice ADR 0147）。全 task done は `gate_ready`＝監査待ちであって完走ではなく、監査待ちが在る限り次アクション面は「残作業なし」と答えない（ADR 0159）
- Peertable 側の用途: 親の受入 gate は audit である（§3.1・決定43）。憲章6の散会宣言が早すぎないことを、親の記憶でなくこの面が支える
- 契約として Lattice に要求するもの: Lattice は**監査の中身を採点しない**こと。accept 記録の存在だけを見る——採点まで持たれると、判断を情報の持ち主に置く円卓の原則が機械側へ吸い上げられる（所有境界の維持。決定46）

### 12.5 単独円卓モードはこの契約の外である

単独円卓モード（決定47・決定50）は Lattice を使わない。したがって上の4面はすべて存在せず、代替は次のとおり:

| 面 | Lattice 併用（既定） | 単独 |
|----|----------------------|------|
| 仕事の取り出し口 | 依存付き ready 一覧 | `.team/tasks.md`（読み取り専用の議題表。依存なし・frontier なし） |
| 着手・完了の記録 | 順序付き start/done journal | room の宣言だけが正 |
| 完了の束縛 | evidence descriptor の digest 検証 | commit と room の完了報告 |
| 完走の判定 | 監査待ち（`audit_pending`）の機械可視化 | 全員の完了報告を親が確認して散会宣言 |

単独モードで失うのは task 間スケジューリングの機械保証と、claim 裁定・完了束縛の機械的根拠である。**失わないのは円卓そのもの**——room・憲章・宣言ベースの協力は最初から Lattice 非依存であり（決定47）、task 内共同作業は Peertable の固有資産である。よって単独モードは、依存構造が浅く短命な作業に限って正当化される。長い campaign・多段の受入・証跡が要る作業では Lattice 併用が既定である。

親番犬のfilter、`SKILL.md`とmember templateまでを同じ変更で揃える。

受入は、(1) `to: "all"`がtyped拒否されmember一覧を漏らさない、(2) 単独DMと複数人宛が従来どおり
保存・配信される、(3) 既存broadcastログを読める、(4) bridgeと親番犬が明示宛先だけを処理する、
(5) 配布物と手順書にbroadcastを案内する経路が残らないこと。

### e2 本番roomへデプロイして再接続を受け入れる

e1の独立監査後、本番room serverを新実装へ切り替える。再起動直前にbellへDMで予告し、親番犬と
各席のwakeup-bridgeがSSE切断後に自動再接続することを実測する。明示宛先の正例、broadcast拒否の
負例、会話ログの保持を本番で確認し、rollback先となる直前imageまたはcommitを記録する。
